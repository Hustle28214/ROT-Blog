## 过程间分析

过程间分析（Interprocedural Analysis, IPA）是指编译器跨函数边界收集信息，用于全局优化的一类静态分析。与只看单个函数体的过程内分析相对，它关心"调用者和被调用者之间发生了什么"。

> 通俗理解：过程内分析像是各家关起门来自查卫生，过程间分析则是把整栋楼当成一个整体来盘点——谁往公共走廊丢了垃圾、谁去邻居家借了锅、谁在楼顶偷偷加建，都要一并考虑。

考虑下面的场景：

```c
int g;              // 全局变量
void f() { g = 1; }
int  h() { return g + 1; }  // 这里的 g 是几？
```

如果只做过程内分析，`h` 里的 `g` 无法常量传播——编译器必须保守假设"任何函数都可能改过 `g`"。有了过程间分析，就能证明 `f` 是唯一的写入点、其值为 1，从而在 `h` 中把 `g + 1` 折叠成常量。跨过程的常量传播、死代码消除、别名判断，都建立在这类信息之上。

## 调用图

过程间分析的第一步是构造**调用图（call graph）**：节点是函数，有向边表示"调用关系"。对直接调用 `foo()` 而言，边是显式的；但一旦出现虚函数、函数指针、回调，调用目标就要依赖**指针分析**来近似解出。

C++ 里的 `shape->draw()`、Java 里的接口方法、C 里的 `qsort(cmp)` 都是这种情况。调用图不准，后续分析全都跟着失真——过度粗糙会让优化机会消失，过度乐观则可能得出错误结论。工业编译器一般采用 CHA（Class Hierarchy Analysis）、RTA（Rapid Type Analysis）等策略来剪掉不可能的目标。

## 上下文敏感与不敏感

一个函数在程序里可能被调用几十次，每次的参数、返回值、副作用都不一样。上下文不敏感的分析把所有调用点**合并**成一个抽象状态，上下文敏感的分析则会**区分**每个调用位置。

```c
int id(int x) { return x; }
int a = id(1);   // a 应为 1
int b = id(2);   // b 应为 2
```

不敏感分析会得出 `id` 的返回值是 `{1, 2}`，于是 `a` 和 `b` 都被认为是 `{1, 2}`；敏感分析则能区分两个调用点，得到 `a = 1`、`b = 2`。常用的敏感策略有 **call-string**（记录长度为 k 的调用栈）和 **object-sensitivity**（用接收者对象作为上下文），代价是状态空间指数膨胀。

## 内联

内联（inlining）是最直接的过程间优化：把被调函数体嵌到调用点，其他过程内优化就能"看穿"函数边界，常量传播、死代码消除、循环优化全都水涨船高。

但内联并非免费。函数被复制多次会导致**代码膨胀**、指令 cache 命中率下降；过大的函数还会拖累寄存器分配。所以编译器会用启发式打分：函数体大小、调用频率（PGO 数据）、是否递归、是否只有一个调用点，共同决定是否值得内联。GCC 的 `always_inline` 和 LLVM 的 `alwaysinline` 属性就是让程序员越过启发式强制开关。

## 指针分析

要弄清"这个指针可能指向哪些对象"，需要**指针分析（points-to analysis）**。两个经典算法给出了不同的精度/性能折中：

- **Andersen 分析**：基于**包含约束**（`p = q` 意味着 pts(p) ⊇ pts(q)），求解等价于图的传递闭包，复杂度 O(n³)，精度高。
- **Steensgaard 分析**：基于**等价合并**（`p = q` 直接令 pts(p) 与 pts(q) 合并成同一集合），用并查集实现，近似线性时间，精度粗。

```c
int a, b, c;
int *p = &a;
int *q = &b;
p = q;      // Andersen: pts(p)={a,b}, pts(q)={b}
            // Steensgaard: pts(p)=pts(q)={a,b}
q = &c;     // Andersen: pts(q)={b,c}, pts(p) 仍={a,b}
            // Steensgaard: 因 p 与 q 已被合并，pts(p)=pts(q)={a,b,c}
```

大型 C 程序通常用 Steensgaard 做首轮筛选，再对热点用 Andersen 精化。

## 逃逸分析

**逃逸分析（escape analysis）**判断一个对象是否可能"逃出"当前函数或线程。如果一个对象的引用没有被返回、没有被存入全局或堆结构，也没有被其他线程访问，那它就是"栈局部"的，可以**栈分配**代替堆分配，还能省掉同步操作。

Java HotSpot 用它做标量替换和锁消除；Go 编译器则明确决定每个变量"逃逸到堆"还是"留在栈"，可以用 `go build -gcflags="-m"` 查看结果。

## 别名分析

**别名分析（alias analysis）**问的是"两个指针 p 和 q 是否可能指向同一块内存"。答案分三种：must-alias、may-alias、no-alias。很多优化的正确性依赖它：如果编译器能证明 `*p` 和 `*q` 不别名，就可以放心把它们的读写重排，甚至并行化循环。C 里 `restrict` 关键字就是程序员给编译器的"保证不别名"承诺。

## 现代实践

工业界的过程间分析越来越倾向**链接期完成**——LLVM 的 **ThinLTO** 和 GCC 的 **LTO** 都把中间表示保留到链接阶段，在整程序范围内做内联和优化。学术界流行用 **Datalog** 声明式地描述指针分析规则，代表工作是 **Doop** 项目，把 Andersen、上下文敏感等策略压缩成几十行规则。**程序切片（program slicing）** 则从某个"感兴趣的语句"反向抽出所有可能影响它的代码，用于调试、验证、安全审计。

## 挑战与局限

过程间分析在遇到**动态特性**时会迅速失效：Python/JavaScript 的运行时类型、Java 反射、C++ 异常、动态加载的插件、多线程共享状态，都会让分析被迫走向最保守的近似。此时要么放弃精度、要么引入**运行时反馈（PGO、JIT 特化）**、要么让程序员用注解（`@Nullable`、`restrict`、`final`）显式帮编译器一把。过程间分析没有银弹，能落地的方案永远是"精度、时间、内存"三者之间的平衡。
