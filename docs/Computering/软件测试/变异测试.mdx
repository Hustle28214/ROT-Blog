# 变异测试：给测试套件下毒来测它自己

一句话说清：故意往被测代码里塞一堆小 bug 生成"变种"（mutant），跑一遍你的测试套件，看有多少变种被抓出来。抓不出来的那部分，就是你的测试套件的盲区。变异测试（Mutation Testing）在 1971 年由 Richard Lipton 提出，思想比它的实用工具早了三十年——直到多核 CPU 普及、编译型语言支持字节码改写，它才真正跑得起来。

它想解决的问题是覆盖率的漏洞：一段代码可以 100% 行覆盖 100% 分支覆盖，但断言全是 `assertNotNull(result)`——这种测试跑完啥也没验证。传统覆盖率只能告诉你"这行被跑到过"，不告诉你"这行错了会不会有人叫"。变异测试补的是后一半：如果代码错了而测试没叫，那测试就是聋子。

## 1. 一个最简单的例子

假设有这样一段代码：

```java
int max(int a, int b) {
    if (a > b) return a;
    return b;
}
```

你写了一条测试：

```java
assertEquals(5, max(5, 3));
```

覆盖率 100%。看起来很牛。现在变异测试往里下毒，生成三个变种：

```
变种 M1: if (a >= b) return a;    // > 改成 >=
变种 M2: if (a < b)  return a;    // > 改成 <
变种 M3: if (a > b) return b;     // 返回值互换
```

- M1 跑 `max(5, 3)` 返回 5，测试通过 → 变种**存活**（survived）
- M2 跑 `max(5, 3)` 返回 3，测试失败 → 变种**被杀死**（killed）
- M3 跑 `max(5, 3)` 返回 3，测试失败 → 变种**被杀死**

M1 存活告诉你：你没写 `a == b` 边界的用例，如果哪天真的把 `>` 写成 `>=`，你的测试根本不知道。这就是变异测试的价值——它是覆盖率骗不了的那一层。想让它闭嘴很简单，补一条 `assertEquals(3, max(3, 3))` 就够了——但你从来没想过要补，是因为覆盖率告诉你已经"测完了"。变异测试的贡献就是把这类被隐藏的盲点挖出来。

## 2. 变异算子

变异算子（mutation operator）就是"往代码里塞什么样的小 bug"的规则。工业界最常用的几类：

| 简称 | 全称 | 干什么 | 例子 |
|---|---|---|---|
| AOR | Arithmetic Operator Replacement | 算术运算符替换 | `a + b` → `a - b` |
| ROR | Relational Operator Replacement | 关系运算符替换 | `a > b` → `a >= b` |
| COR | Conditional Operator Replacement | 逻辑运算符替换 | `a && b` → `a \|\| b` |
| LCR | Logical Connector Replacement | 位运算符替换 | `a & b` → `a \| b` |
| ICR | Inline Constant Replacement | 常量替换 | `return 0` → `return 1` |
| VMR | Void Method Removal | 删掉一次方法调用 | `list.clear();` → `;` |
| RVR | Return Value Replacement | 返回值改成默认值 | `return x` → `return null` |
| NCR | Negate Conditional | 条件取反 | `if (x)` → `if (!x)` |
| ABS | Absolute Value Insertion | 数值取绝对值 | `x` → `Math.abs(x)` |
| UOI | Unary Operator Insertion | 插入一元运算符 | `x` → `-x` 或 `!x` |
| SBR | Statement Block Removal | 删掉一个语句块 | `{ f(); }` → `{}` |

这些算子的选择不是随便定的，它模拟了程序员真实会犯的错误——把 `>` 写成 `>=`、把 `&&` 写成 `||`、忘记调用一个 side-effect 方法。这也是变异测试的假设，叫 **competent programmer hypothesis**：真实 bug 大多和正确代码只差一点点。所以下毒下大了没意义（比如把整个函数体删掉），太容易被杀，反而检验不出测试套件的敏感度。

另一条重要假设叫 **coupling effect**：能杀死简单变种的测试通常也能抓到复杂 bug。这条假设是变异测试成立的根基——如果不成立，那测简单变种就没意义。实证研究（Andrews 等，2005）在几个开源项目上验证：mutant 检测率和真实 bug 检测率强相关，coupling effect 大致靠谱。

不同工具支持的算子集合不一样。PIT 默认打开约 12 个"稳定"算子，全打开有 40+ 个但会产生大量等价变种。工程上一般用默认集合起步，等团队适应了再逐步加入更激进的算子。

一个进阶话题是 **higher-order mutation**：不只改一处，一次改两处或更多。理论上高阶变种数是低阶的组合爆炸，但实证发现高阶变种里有很多"subsuming mutants"——杀死它同时也杀死若干低阶变种，压缩了总的变种数量。这条路在学术界很火，工业工具支持还有限。

## 3. Mutation Score 和让人头大的等价变种

**Mutation Score** 的定义很直白：

```
mutation_score = killed / (total - equivalent)
```

分子是被杀死的变种数，分母是"能被杀死的"变种总数——扣掉 equivalent mutants。

Equivalent mutant（等价变种）是变异测试的老大难：改了代码但语义没变，任何输入都产生一样的输出，所以永远杀不死。例子：

```java
// 原代码
for (int i = 0; i < list.size(); i++) { ... }

// 变种：< 改成 !=
for (int i = 0; i != list.size(); i++) { ... }
```

如果 `i` 从 0 递增到 `list.size()`，`<` 和 `!=` 在所有可达状态下等价。这个变种不管你怎么测都杀不死，但它不是测试套件的漏洞——它是编译器可以自由重写的等价代码。

再举个更隐蔽的：

```java
// 原代码
int x = a + 0;

// 变种：+ 改成 -
int x = a - 0;
```

`+ 0` 和 `- 0` 语义完全一致，怎么测都不会区分。这类小学生等级的等价变种其实好识别，工具能自动剪枝掉。真正麻烦的是那些需要理解业务语义才能判定的等价变种，比如：

```java
// 原代码
if (users.size() > 0) processAll(users);
// 变种
if (!users.isEmpty()) processAll(users);
```

两条都对，但工具单独看不知道 `size() > 0` 和 `!isEmpty()` 等价——除非有专门的规则库告诉它。

理论上判断两个程序是否语义等价是**不可判定问题**（reducible to halting problem），所以没有算法能完美识别等价变种。工业做法：

- 静态分析剪枝一部分明显等价的（如死代码变异、数据流不可达）
- 编译器优化后指令级 diff——如果 optimizer 把两版编成一样，那就是等价
- 剩下的靠人工审阅——review 幸存变种时手工标记
- 上限估计：DeMillo 等人的经验数据大约 5–10% 的变种是等价的

于是很多团队直接用没扣等价变种的分数（有时叫 mutation coverage），只在跨版本对比时才关心绝对值。80% 的 mutation score 已经算相当好，很少有人追到 95%——最后那 15% 大概率全是等价变种在打转，硬追反而害人。

## 4. Trivial mutants 和 subtle mutants

不是所有变种都同样值钱。粗略分成两类：

- **Trivial**：任何一个像样的测试都能杀。例如把 `return true` 改成 `return false`，几乎所有断言都会挂
- **Subtle**：需要精确的边界或特定输入才能暴露。例如 `>` 改 `>=`、`i - 1` 改 `i`

好测试套件应该能杀 subtle mutant，光杀 trivial 说明测试大而无当。PIT 有个报告字段 `MUTATION_COVERAGE`，把杀死数按算子分类展示——如果 AOR 里 `+` 改 `-` 的杀率是 100%（因为随便算个错的结果都会不匹配），而 ROR 里边界替换杀率只有 30%，那你的测试套件是"结果导向"的，缺"边界导向"的用例。这个分层能指导团队精准补测试。

## 5. 主流工具

各语言的变异测试工具生态：

| 工具 | 语言 | 特点 |
|---|---|---|
| PIT (Pitest) | Java/Kotlin | 字节码级变异，速度快，工业标准 |
| Mutmut | Python | 源码级 AST 改写，Django/Flask 项目常用 |
| MutPy | Python | 学术界起步，算子更全 |
| Stryker | JavaScript/TypeScript/C# | 前端圈的事实标准，报告好看 |
| Mull | C/C++ | 基于 LLVM IR，编译期插入变种 |
| Cargo-mutants | Rust | 后起之秀，速度尚可 |
| Cosmic Ray | Python | 支持分布式执行 |
| Infection | PHP | Laravel 生态用得多 |
| μJava / Javalanche | Java（历史） | 学术祖师爷，现在被 PIT 取代 |
| Descartes | Java | 极简算子集合（只做 RVR），跑得飞快 |

PIT 值得单独说一句——它不改源码，直接在 JVM 字节码层面改指令然后重新加载类，省去了每次改一行都要重新编译的巨大成本。对一个中等规模 Java 项目，PIT 跑一遍从几小时压到十几分钟是它统治 Java 生态的核心原因。它的作者 Henry Coles 后来创立了 Descartes 项目，把这个思路推到极端——只用一个算子（把方法体替换成 `return default`），实测覆盖率没跌太多但速度上一个数量级，验证了"少量高质量算子 > 全量算子"的经验规律。

## 6. 计算成本：变异测试贵在哪

朴素做法的成本是 $N \times T$，其中 $N$ 是变种数，$T$ 是测试套件耗时。一个 10 万行代码的项目变种数轻松上百万，测试套件跑一次 10 分钟——直接算是二十年。所以变异测试从 1971 年提出到 2010 年代才实用化，中间的鸿沟全靠工程优化填：

**1. 变种采样（sampling）**：不跑所有变种，随机抽 10%。牺牲精度换速度，适合日常 CI。研究表明 10% 采样能保持 80%+ 的准确度。

**2. 弱变异（weak mutation）**：变种运行到变异点之后立即检查内部状态，不用等测试跑完看断言。中间状态不同就算杀死。速度快但可能漏杀。

**3. 增量变异（incremental mutation）**：只对本次 diff 涉及的行做变异，配合 [精准测试](./精准测试.mdx) 里的 test impact analysis 一起用，CI 里从跑几万个变种降到几百个。PIT 有个 `--historyInputLocation` 参数专门做这个，只重跑变化的类。

**4. 变异并行化**：每个变种之间完全独立，天然可以铺开到 N 台机器。PIT 支持多线程，Stryker 支持进程池，Cosmic Ray 支持 Celery 分布式。

**5. First-fail 短路**：一旦某个测试杀死了这个变种，立即停止跑剩下的测试。因为你只关心"杀 or 不杀"，不关心"几个测试杀的"。这个优化通常能省 3–5 倍时间。

**6. 变种去重**：AST 分析发现某些变种在语义上重合（如 `x + 0` 变成 `x - 0` 和 `x - 0` 变成 `x + 0`），只跑一次。有工具做 **trivial compiler equivalence (TCE)**：把两个变种都编译一遍，字节码相同就归为等价。

**7. 预测式变异**：机器学习模型看代码上下文预测"这个变种大概率被杀 / 存活"，只跑不确定的那部分。学术界的 PredMutation 之类工作在探索。

**8. Split execution**：把变种按测试相关性分组，每组只跑相关测试。前提是有个 test impact 映射（回到了 [精准测试](./精准测试.mdx) 的话题）。

结合以上，工业实践里一次变异测试从"几周"压缩到"几十分钟"，从"跑一次崩一次"变成"每周一次 CI job"。

## 7. 变异测试 vs 覆盖率

变异测试和 [白盒测试](./动态测试：白盒测试.mdx) 里讲的覆盖率是什么关系？覆盖率是下限，变异测试是上限。

- **行/分支覆盖率**衡量"测试是否路过"
- **变异测试**衡量"测试是否会尖叫"

两者能捕捉的问题维度不同。极端例子：一段被 100% 覆盖但完全没断言的测试，行覆盖率是满分，mutation score 接近 0——所有变种都能存活，因为没人检查输出。反过来，一段 mutation score 80% 的代码，覆盖率一定不低——变种要被杀死，测试至少得跑到那一行。所以实际使用是：

1. 先用覆盖率保底：低于阈值（比如 70% 行覆盖）拒绝合并
2. 关键模块再上变异测试：核心 domain 逻辑、支付计算、权限判断这类要求 mutation score > 70%
3. 全项目跑变异测试成本太高，只在核心目录跑
4. 变异测试作为**季度审计**而非**PR 卡点**——每周或每月跑一次，产出报告让团队补测试

变异测试对 team culture 的作用有时比技术作用更大。第一次跑完看到大家精心写的测试杀率只有 30%，是很好的清醒剂——让写测试的人从"数量"关注到"质量"。

## 8. 局限

变异测试不是银弹，有几个绕不开的问题：

**成本**是最大的门槛。即便用了采样、并行、增量，一个中型项目的变异测试 CI 也常要几十分钟。团队心理承受的 CI 时间上限大概是 15 分钟，超过就会开始寻找绕过它的办法。

**等价变种**处理不干净会让 mutation score 天花板卡在 85–90%，追求 100% 是自欺欺人。有些团队因此从"绝对分数"转向"相对进步"——每周比上周多杀 5 个变种。

**语义变异有限**：现有算子基本都在语法/运算符层面，捕捉不了业务逻辑错误。比如"折扣计算应该在税前而不是税后"——这种错误任何算子都变不出来，因为它是设计层面的错误。变异测试测的是"代码写对了没"，不是"设计对不对"。

**假杀（false kill）**：有些测试碰运气挂了（时序、随机数、外部依赖），把变种当成被杀死，实际测试并没有真正检查语义。这跟 flaky test 是同一个病灶——想上变异测试，先修 flaky test。

**读起来累**：mutation testing 的报告是一堆 `line 42: replaced > with >=`，需要工程师逐个看，判断"这个变种存活是坏事还是无所谓"。没人 review 就是纯粹的浪费。工业界的一个折中：只 review PR diff 中新引入代码的存活变种，不 review 历史代码——控制心智负担。

**大团队 buy-in 难**：变异测试暴露的是"你的测试写得不好"，是一种批评。团队会本能抵抗——先说服工程师"覆盖率不够、变异测试更严"，是社会工程学问题不是技术问题。

## 9. 变异测试在测试家谱里的位置

变异测试的定位是**元测试（meta-testing）**——它测试的不是被测代码，而是测试代码本身。同样在这一层的还有：

- [静态测试技术](./静态测试技术.mdx)：也测代码本身，但只看语法/规则，不跑
- [白盒测试](./动态测试：白盒测试.mdx) 的覆盖率：粗粒度的测试质量指标
- [基于模型的测试](./基于模型的测试.mdx)：从规格自动生成测试，另一个方向弥补测试盲区
- [模糊测试](./模糊测试.mdx)：用输入侧的多样性找 bug，变异测试用代码侧的多样性找测试盲区
- Fault injection：跟变异测试同源，但改的是运行时状态（网络延迟、磁盘错误），不是源码
- Property-based testing（Hypothesis、QuickCheck）：输入侧的补充力量，两者一起能大幅提高测试质量
- [精准测试](./精准测试.mdx)：可以复用变异测试的映射数据，两者数据管道有共性

变异测试比覆盖率严格，比形式化验证便宜，是当前工业界能落地的最强测试质量指标。真正把它跑起来的团队不多，但跑过的团队普遍反馈：第一次跑完看到 mutation score 只有 30% 会挺尴尬——原来我们写的那么多测试，一半都是形式主义。往前追溯这个思想的源头可以到 fault-based testing 的历史线，往后延伸到自动化程序修复（automated program repair，APR）——APR 里的"生成候选修复"用的就是变异算子的反向操作。变异测试和 APR 是同一枚硬币的两面：一个把好代码变坏来测测试，一个把坏代码变好来修 bug。
