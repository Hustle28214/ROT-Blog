# 探索性测试：把测试员当研究员用

探索性测试（Exploratory Testing，ET）想说的事情不复杂：软件太复杂、需求变化太快、脚本写得再全也漏得掉，与其把测试员当成执行工，不如让他边测边学、边设计、边发现——学习、设计、执行三件事并行发生。概念由 Cem Kaner 在 1988 年的《Testing Computer Software》里正式提出，James Bach 后来把它发扬成一整套方法论 Rapid Software Testing（RST）。

## 1. 什么是探索性测试

先说清楚 ET 之前测试员是怎么工作的，才能理解为什么"边测边学"算是一种新姿势。

传统脚本化测试（Scripted Testing）的流程是：需求评审 → 写测试用例 → 走查评审 → 执行 → 记录结果。测试员在执行阶段基本是照本宣科，一个用例走完打个 Pass/Fail，不允许"临场发挥"。这套流程有个隐含假设：需求是稳定的、可穷举的，用例作者能预先想清楚所有该测的事。

ET 挑战的正是这个假设。Cem Kaner ��原话大致是：测试是一个**认知过程**，不是一个执行过程。测试员在测的过程中会不断产生新问题——"这个字段填负数会怎样？"、"如果我在提交的一瞬间断网？"——这些问题在写用例阶段根本想不到，只有真的把手放在软件上才会冒出来。

一个简单的对比：

| 维度 | Scripted Testing | Exploratory Testing |
|---|---|---|
| 设计时机 | 事先写好 | 测试时同步设计 |
| 输出物 | 测试用例文档 | Charter + Session 记录 |
| 依赖 | 需求稳定、用例完备 | 测试员经验、直觉、好奇心 |
| 变更响应 | 需求一改用例全改 | 无所谓，Charter 即时调整 |
| 度量 | 用例通过率 | 覆盖领域、发现的问题数 |
| 追溯性 | 强，用例 ↔ 需求 | 弱，靠日志和笔记 |
| 适合场景 | 回归、合规、外包 | 新功能、复杂交互、UI |

要强调的是：ET 不是"随便点点看"（那是 ad-hoc testing）。ET 是有结构的，有 charter、有时间盒、有事后复盘，只是把设计从"事前"挪到了"测试当下"。

## 2. Session-Based Test Management

光说"边测边学"太虚，James 和 Jon Bach 兄弟提出了 SBTM 来把 ET 落地成可管理的活动。核心是**用 Session 这个时间盒把测试切块**。

一个 Session 的三要素：

- **Charter**（章程）：这次要探什么。一两句话说清目标，避免漫无边际。
- **时间盒**：60 到 120 分钟。太短来不及进入状态，太长注意力涣散。
- **Debrief**（复盘）：Session 结束和测试主管过一遍——发现了什么、下一步测什么、有没有新 charter。

Session 里测试员做三件事，SBTM 用 TBS 划分时间比例：

| 活动 | 占比 | 内容 |
|---|---|---|
| Test（测试） | 一般 60%+ | 实际操作软件、观察、思考 |
| Bug investigation | 视情况 | 复现、隔离、写缺陷单 |
| Setup | 视情况 | 环境搭建、数据准备、工具切换 |

TBS 比例本身就是 debrief 的输入——如果一个 session 里 setup 占了 50%，说明测试环境有问题，值得单独立个任务优化。

## 3. 一个 Charter 长什么样

抽象说完了，看具体的。假设我们在测一个电商 App 的"优惠券叠加"功能，一个 Charter 可能长这样：

```
Charter #E-217
探索目标：验证优惠券叠加规则在不同用户等级、不同商品品类下的行为
时长：90 分钟
测试员：Cailey
构建版本：v3.14.2-rc1
测试环境：staging-cn
Session 笔记文件：sessions/2026-08-25-e-217.md
```

Charter 只回答"探什么"，不回答"怎么探"。"怎么探"是测试员在过程里自己拿主意的。

Session 结束时的记录（节选）大致这样：

```
[00:00] 用银牌用户 A 加满减券 + 品类券，购物车两件同品类商品。
        结果：叠加成功，实付 89.00，符合规则。
[00:12] 换金牌用户 B，同样两张券。
        发现：金牌专享券自动置于最优位置，普通品类券未叠加。
        问题？—— 记为 Q-1，需与 PM 确认是否符合设计。
[00:35] 尝试极端组合：4 张券（1 满减 + 2 品类 + 1 会员日）。
        崩溃：结算页 loading 无响应，30 秒后前端弹 "网络异常"。
        实际后端 200 OK，前端未处理 promotions 字段的空数组。
        Bug #B-4491 已提。
[01:02] 切游客态。发现下单流程绕过券选择直接提示"请登录"。
        流程本身正确，但登录回跳丢失了购物车。
        Bug #B-4492 已提。
...
[01:30] Session 结束。
```

Debrief 时测试主管会问几个问题：这个 session 的 TBS 大致什么比例？有没有触发新的 charter？发现的 bug 有没有共性？——比如 B-4491 和 B-4492 都是前端对边界响应处理不当，可能整个前端团队值得做一次针对性 code review。

Charter 的粒度也是有讲究的。太粗（"测优惠券模块"）会让 session 失焦；太细（"测银牌用户使用满 100 减 10 券"）就退化成脚本用例了。经验值是：一个 charter 让一个熟悉业务的测试员正好能在 90 分钟内探得七七八八。

## 4. 探索者的启发式方法

ET 说依赖测试员的经验，但经验不是玄学。James Bach 总结了一堆启发式（heuristics）帮测试员系统地产生想法。最有名的是 **SFDPO**（也叫 San Francisco Depot）—— Structure、Function、Data、Platform、Operation：

| 维度 | 问自己 |
|---|---|
| Structure | 系统由哪些组件组成？每个组件单独测过吗？ |
| Function | 每个功能设计上要做什么？边界在哪？ |
| Data | 输入数据有哪些种类？极端值、空值、超长？ |
| Platform | 依赖哪些外部环境？浏览器、OS、网络、时区？ |
| Operation | 用户会怎么用？谁在用？什么场景？ |

再比如 **CRUSSPIC STMPL**（快感/可靠性/可用性/安全/性能/可安装/兼容 + 支持/可测/可维护/可移植/本地化）—— 一个记忆锚点，用来提醒自己别只测功能忘了非功能。

启发式的作用不是给答案，而是**在你脑子空白的时候提示你下一个该问什么问题**。这就是"边测边设计"的具体形态。

## 5. 为什么敏捷时代 ET 特别重要

脚本化测试的前提是需求稳定。可敏捷开发迭代两周一版，每 Sprint 需求都在变，一个 Sprint 里写完 200 条用例，下个 Sprint 一半就作废了。这种节奏下写详细用例是明显的浪费。

对比一下测试用例作为产出物在两种模式下的生命周期：

| 模式 | 用例生命周期 | 用例价值 |
|---|---|---|
| 瀑布 | 数月到数年 | 高，回归时反复用 |
| 敏捷 | 一到两个 Sprint | 低，往往就用一次 |

ET 的产出物是缺陷 + Session 笔记，不是用例文档，天然适应变更。同时 ET 强调测试员和开发的对话（很多问题在 debrief 或 pair test 里就当场解决了），这个正好和 Scrum 的 whole team approach 吻合。所以在 [敏捷测试](./敏捷测试.mdx) 的四象限里，Q3 象限（面向业务、批判产品）几乎全靠 ET。

不过要注意：ET 不是替代自动化测试，而是补充。回归还是要靠 [自动化测试](./自动化测试.mdx) 兜底，把机器擅长的重复劳动交给机器，把人的头脑用在机器不擅长的"下一步该测什么"上。

## 6. 探索性测试和其他测试的关系

ET 常被拿来和几个近亲比：

- **Ad-hoc testing**：没有 charter、没有时间盒、没有记录。ET 是有结构的 ad-hoc。
- **[黑盒测试](./动态测试：黑盒测试.mdx)**：黑盒是从"看不看得到内部"的角度分类，ET 是从"设计时机"的角度分类。ET 通常是黑盒的，但也可以做灰盒 ET（测试员懂点代码、看 log、看 DB）。
- **Session-based ET**：本文讲的 SBTM 版本。也有不打 session 的自由 ET，管理起来更松散。
- **[基于模型的测试](./基于模型的测试.mdx)**：MBT 是把探索过程"外化"给了模型和工具，思路正好相反。两者可以互补。

## 7. 局限

不要把 ET 当银弹。它有几个明显的软肋。

**难以度量**。ET 的产出是"发现"，可发现本身很难量化。管理者习惯问"这周你测了多少用例、通过率多少？"—— ET 给不出这种数字。可以给 session 数、bug 数、覆盖的 charter，但这些指标和"质量"的对应关系比用例通过率还弱。

**依赖测试员的水平**。ET 的效果几乎完全取决于测试员的经验、直觉、领域知识。同一个 charter 交给两个不同的测试员，产出可以差一个数量级。这让 ET 很难外包、很难新人上手、很难标准化。

**追溯性弱**。医疗、航空、金融这些强合规行业需要能拿出"我们测了 XX 需求的 XX 条件"的证据。ET 的 session 笔记做不到 IEC 62304、DO-178C 那种可追溯要求。这时候必须回到脚本化用例。

**回归代价高**。ET 每次探完的知识都在测试员脑子里，下一版发布还得重新探一遍。所以回归必须交给自动化，ET 只负责"新东西"和"人才能发现的东西"。

**Session 记录本身是负担**。要写清楚、要复盘、要归档，写得不好等于白测。很多团队试点 ET 失败就是因为 session 记录没坚持，最后蜕化成了 ad-hoc。

## 8. 在测试家谱里的位置

往前看，ET 继承了 Kaner "context-driven testing" 学派的核心信念——测试是一门认知活动而非流程活动。往后看，它把这份信念输出给了整个敏捷测试生态：

- [敏捷测试](./敏捷测试.mdx)：把 ET 塞进 Sprint，成为 Q3 象限的主力
- [自动化测试](./自动化测试.mdx)：处理 ET 探完之后需要回归保护的部分
- [基于模型的测试](./基于模型的测试.mdx)：另一个方向的探索——用工具外化探索过程
- [模糊测试](./模糊测试.mdx)：机器版本的探索，随机输入 + oracle 检测
- [测试管理](./测试管理.mdx)：Charter/Session/Debrief 是 SBTM 交给测试管理的三件套

ET 的价值观最终会渗透到怎么组织测试团队、怎么做 [测试过程与生命周期](./测试过程与生命周期.mdx)、怎么衡量测试员。它不是一个可选工具，而是一种默认底色——即使你的团队 90% 时间在跑脚本，剩下 10% 的探索也常常发现最难缠的 bug。
