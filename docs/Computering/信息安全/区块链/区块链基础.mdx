## 区块链基础

在讨论智能合约、共识、DeFi 之前,我们先把最底下的三块积木搭起来:哈希函数、Merkle 树、以及把它们串起来的"链"结构。这三样东西凑在一起就是"区块链"这个名字的全部含义。

### 从哈希函数说起

假设我们想给一份文档做一个"指纹":任意改动一个字节,指纹就要完全不同,而且从指纹不能反推出原文。这个想法用密码学的话说,就是哈希函数。一个合格的哈希函数 $H$ 应该同时满足三条:抗原像(给指纹反推不出原文)、抗第二原像(给一份原文找不到另一份指纹相同的原文)、抗碰撞(整个空间里找不到两份指纹相同的原文)。

比特币用的是 SHA-256,以太坊用 Keccak-256。它们的具体实现有差别,但我们只需要记住,它们都有一个非常重要的性质叫雪崩效应:输入改一位,输出几乎完全变。用几行 Python 就能感受到。

```python
import hashlib

def h(x):
    return hashlib.sha256(x.encode()).hexdigest()

print(h("hello"))
print(h("hellp"))
```

两次输入只差一个字母,输出却完全不像。区块链所有防篡改保证的根都长在这里——一旦我们把某份数据的哈希公开出来,想改这份数据而不被发现就变得非常困难。

### 从哈希到工作量证明

有了哈希,我们再往前走一步。假设我不仅想给一份数据一个指纹,还想让"生成这个指纹"这件事本身要付出一点成本,该怎么办?

一个巧妙的做法是,要求哈希值有一定形状。比如说,我们规定哈希值前 20 个二进制位必须都是 0。因为哈希不可预测,想让输出符合这个形状,只能不停改输入试。下面这段代码演示了这个过程。

```python
import hashlib

def mine(data, difficulty):
    target = "0" * difficulty
    nonce = 0
    while True:
        h = hashlib.sha256(f"{data}{nonce}".encode()).hexdigest()
        if h.startswith(target):
            return nonce, h
        nonce += 1

print(mine("block#1", difficulty=5))
```

难度每加 1,期望的尝试次数就翻 16 倍。这就是比特币矿工在做的事情,也是"算力"这个词的物理含义。共识机制那一节我们会更详细地讨论它,这里先记住:哈希是可以被"变贵"的。

### Merkle 树:让轻客户端也能验证

一个区块里可能装了几千笔交易,如果每个用户都要下载全部交易才能验证钱包余额,手机就没法用。我们想要一种更经济的验证方式:只下载少量数据,也能确认某一笔交易确实在区块里。

Merkle 树解决的就是这个问题。我们把所有交易两两配对,每对哈希一次,得到上层的节点;再两两配对、哈希,直到剩下一个根。这个根我们称为 Merkle Root,只有 32 字节。

```
                Root = H(H12 || H34)
                /                    \
        H12 = H(H1||H2)         H34 = H(H3||H4)
         /    \                    /    \
      H1=H(tx1) H2=H(tx2)      H3=H(tx3) H4=H(tx4)
```

现在假设我想向别人证明 $tx_3$ 在这棵树里,该怎么做?我不需要把整棵树给他,只需要给他两个哈希:$H_4$ 和 $H_{12}$。他从 $tx_3$ 出发,先算 $H_3 = H(tx_3)$,再算 $H_{34} = H(H_3 \| H_4)$,最后算 $Root = H(H_{12} \| H_{34})$,和已知的根一比,一致就说明 $tx_3$ 确实在树里。整个验证只做了 $\log n$ 次哈希。

这套构造在实际系统里应用极广。以太坊的空投白名单就是一个典型用法:项目方把几万个白名单地址算成一棵 Merkle 树,只把 32 字节的 root 存到合约里,其余数据都放到 IPFS 或 GitHub。用户领空投时提交自己的 proof,合约在链上验证。

```solidity
import "@openzeppelin/contracts/utils/cryptography/MerkleProof.sol";

bytes32 public root;

function claim(bytes32[] calldata proof) external {
    bytes32 leaf = keccak256(abi.encodePacked(msg.sender));
    require(MerkleProof.verify(proof, root, leaf), "not in whitelist");
    // ...发奖励
}
```

一份 10 万人的名单,只往链上写 32 字节,就完成了任意成员的验证。这就是 Merkle 树的魅力。

### 区块结构:把这些拼起来

现在我们看比特币的一个区块头长什么样。它一共 80 个字节,由几个字段组成。

```
version         4B
prevBlockHash   32B  <- 上一个区块的哈希
merkleRoot      32B  <- 本块所有交易的 Merkle Root
timestamp       4B
bits            4B   <- 难度目标
nonce           4B
```

最关键的字段是 $prevBlockHash$。它把当前区块和前一个区块绑在了一起:改动第 100 块的任何一位,它自己的哈希就变;而第 101 块里存着"第 100 块的哈希",对不上;于是第 101 块也要被重挖,101 变了 102 又要重挖,如此雪崩下去,直到追上当前最新的区块。想篡改历史,攻击者必须重新做完从篡改点到现在的所有工作量证明。这就是"区块链不可篡改"这句话的机制。

以太坊的区块头会多几个字段(stateRoot、receiptsRoot、transactionsRoot 三棵不同的树),但整体思路完全一样:每一块都指向上一块,每一块都对当前状态做一个可验证的承诺。

### 两种记账模型

到目前为止我们只讨论了交易怎么被记录,还没讨论"账本"里长什么样。这里有两条不同的技术路线,值得放在一起对比。

第一种是比特币用的 UTXO(未花费交易输出)模型。你并不"拥有余额",你拥有的是一堆 UTXO——每一个 UTXO 是某笔历史交易输出到你的一笔具体金额。花钱时,你消费掉若干 UTXO 作为输入,产出若干新的 UTXO 作为输出;剩下的部分作为找零回到自己钱包。钱包软件把你所有的 UTXO 加起来,就是屏幕上显示的"余额"。这种模型的好处是天然并行——处理不同 UTXO 的两笔交易之间完全无冲突;缺点是编程模型比较陌生。

第二种是以太坊用的账户模型。每个地址就是一个账户,账户上直接维护余额,转账就是从 A 账户减去、B 账户加上。这种模型对写合约的人非常友好——它就像我们日常理解的银行账户。代价是并发差:同一个账户的两笔交易只能串行执行,而且需要引入 nonce 来防止重放。

Nonce 的存在是账户模型下一个很微妙的安全字段。每笔交易都要带一个 nonce,节点只接受严格递增的 nonce。如果没有这个字段,任何人拿到你签好的一笔转账都可以反复播放,把你钱包扫空。而且这里还有一个隐藏问题:如果你在一条链上签了 nonce=5 的交易,理论上有人可以把这笔完全一样的字节流拿到分叉链上重放。以太坊后来在 EIP-155 里把 chainId 塞进了签名,这才把跨链重放堵住。

### 最终性

一笔交易上链之后,多久算是"不可撤销"了?这个问题的答案在不同共识下不一样,值得单独说一说。

在 PoW 系统里,最终性是概率意义上的:随着后面追加的区块越多,交易被回滚的概率指数衰减。交易所在收比特币充值时通常要等 6 个确认,大约 1 小时,并不是拍脑袋定的数字,而是这个时间窗口内被回滚的概率已经足够小。

在 BFT 系的 PoS 里,最终性是确定的:一旦超过 2/3 的验证者签名,这个块就永远不会被回滚,除非 1/3 以上的验证者被 slash 掉。理论上这个成本大到"永不发生"。以太坊合并后的 finalize 就是这种。

这两种最终性对应的安全模型很不一样。前者下的 51% 攻击可以做双花,但不能凭空造币;后者下的 33% 攻击可以让链停摆,但要付出天价的质押作为攻击成本。哪种更安全其实取决于你怎么定义"安全"。

### 状态、交易、事件

最后一节我们厘清三个初学者容易混淆的概念,后面讨论合约时会反复用到。

状态(state)是所有账户余额和合约变量的当前快照。以太坊把状态存在一个叫 Merkle Patricia Trie 的结构里,每个状态版本都有一个 32 字节的承诺(stateRoot),放进区块头。

交易(transaction)是状态变更的输入。它由用户签名,广播到网络,被打包进区块并按顺序执行,得到新的状态。

事件(event)是合约在执行过程中主动"广播"的日志。它不进状态,但会被打包在交易的回执里,永久可查。前端 dApp、区块浏览器、The Graph 之类的索引器几乎都靠事件感知状态变化,因为读事件比读状态便宜得多。

新人常犯的一个 bug 是"只 emit 事件,没改 storage"——事件是通知,不是数据源;链上真正的状态是 storage,不是 log。这一层分清楚了,再看合约代码就会顺很多。

### 小结

区块链的底层就是这么几件事:哈希函数提供不可篡改性,Merkle 树把大量数据压缩成一个可验证的根,链式结构把每一个块和它的历史绑在一起。这三件事再加上后面要讲的共识机制,就构成了整个区块链系统的骨架。

我们讨论的每一项技术都不是新东西——哈希函数、Merkle 树都是几十年前的密码学工具。中本聪的贡献是把它们组合在一起,加上工作量证明的经济激励,让"无许可的分布式账本"第一次真正跑起来。
