## 1. 机器人里的“决策”到底在解决什么

机器人上层软件常被拆成感知 → 决策 → 控制。决策层要回答的不是“关节该转多少度”，而是：

- 现在该做哪一步？
- 做不下去时换什么策略？
- 环境突变时要不要打断当前动作？

如果把这些问题全塞进一个巨型 `if-else` 或一张扁平状态机里，系统会很快变得不可维护。行为树（Behavior Tree, BT）的定位是：**把复杂任务拆成可组合的树形决策执行器**，擅长“按优先级与顺序执行决策”，而不是做长时域最优规划。

## 2. 和常见决策范式比一比

| 范式 | 强项 | 弱项 | 典型角色 |
| :--- | :--- | :--- | :--- |
| **FSM** | 局部状态清晰、实现简单 | 状态爆炸、跳转难维护 | 局部模式切换 |
| **行为树** | 可组合、可读、易打断与复用 | 不擅长长时域规划 | **执行层** |
| **GOAP / HTN** | 可规划、目标驱动 | 实时性与工程成本更高 | **规划层** |
| **Utility AI** | 多目标权衡、平滑选择 | 调试阈值、边界难控 | **评分 / 选择** |
| **LLM Agent** | 语义理解、开放任务 | 延迟、幻觉、不可控 | **高层意图 / 脚本生成** |

一句话：**BT 适合执行决策，不擅长单独承担长时域规划。** 工程上常见做法是“规划器出计划，行为树负责稳健执行与反应”。

## 3. 行为树不是状态机流程图

常见误解：把 BT 画成“带分支的流程图”，就当成高级 FSM。

关键差别：

1. **组合语义**：Sequence / Selector / Decorator 是可嵌套的控制流算子，不是手写边。
2. **Running 跨帧**：节点可以返回 Running，下一 tick 从“正在跑”的位置继续，而不是每帧从状态图重判一遍。
3. **反应式中断**：条件变化可以打断正在执行的分支（Observer Abort 等），这是 BT 的核心能力之一。

把 BT 当流程图用，通常会丢掉 Running、黑板和中断，最后写出一棵“看起来像树的状态机”。

## 4. 机器人场景里 BT 特别合适的地方

- 操作任务：接近 → 抓取 → 抬起 → 放置，失败则重试或换策略
- 导航任务：规划路径 → 跟随 → 避障 → 重规划
- 人机协作：等待指令 → 确认安全 → 执行 → 异常上报
- 多技能调度：空闲巡检 / 充电 / 执行任务之间的优先级切换

这些场景共同点是：**步骤清晰、需要频繁反应、要可调试可复用**，正好落在 BT 甜点区。

## 6. 本篇小结

1. BT 是树形组合的**决策执行器**，不是状态机流程图。
2. 相对 FSM：更可组合；相对 GOAP/HTN：更偏实时执行；相对 Utility：更偏结构化控制流。
3. 机器人落地时，优先把 BT 放在执行层，规划与评分交给别的模块。
