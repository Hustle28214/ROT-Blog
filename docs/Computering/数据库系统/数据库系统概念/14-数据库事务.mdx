## 17.1 事务的概念

**事务（transaction）** 是数据库系统中一组数据访问与更新操作构成的执行单元，从用户的角度看是一个"要么全做、要么不做"的原子逻辑动作。经典的银行转账例子最能说明事务的必要性：

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 'A';
UPDATE account SET balance = balance + 100 WHERE id = 'B';
COMMIT;
```

若在扣减 A 与增加 B 之间系统崩溃，A 的钱扣掉了却没进 B，账目将永远不一致。为避免这种情形，DBMS 必须保证事务具备四条性质，通常称为 **ACID**：

| 缩写 | 名称 | 含义 | 主要机制 |
| --- | --- | --- | --- |
| A | 原子性 (Atomicity) | 事务内所有操作要么全部提交、要么全部撤销 | 回滚日志、UNDO |
| C | 一致性 (Consistency) | 事务将数据库从一个一致状态转为另一个一致状态 | 应用程序 + 完整性约束 |
| I | 隔离性 (Isolation) | 并发事务的中间状态互不可见 | 并发控制协议（锁、时间戳、MVCC） |
| D | 持久性 (Durability) | 事务一旦提交，其影响永久保存，不因崩溃而丢失 | 重做日志、WAL、持久化到非易失存储 |

其中，一致性主要是"应用逻辑 + 约束"的责任，DBMS 只保证在满足其他三条性质的前提下不会引入不一致；A、I、D 则完全是 DBMS 的职责。

进一步展开这四条性质：

- **原子性** 保护应用程序免于"部分写入"的困扰。用户不必在应用层维护复杂的回滚逻辑：只要事务显式或隐式中止，之前所有已经生效的更新都会被自动撤销。
- **一致性** 是应用与 DBMS 的共同契约。DBMS 只强制主键、外键、`CHECK`、`NOT NULL`、`UNIQUE` 等**声明性约束**；诸如"余额转账后总额不变"这类**语义性约束**必须由事务作者书写正确。
- **隔离性** 让应用可以在单事务视角下思考，仿佛整个数据库只有自己在使用；实际的并发调度由 DBMS 内部并发控制器完成。
- **持久性** 要求已提交的更新必须写入稳定存储；即便机器立即掉电，重启后重放日志仍可恢复。

一个完整的事务通常还需应用层与 DBMS 层协同完成：应用先声明事务边界，然后按照业务逻辑读写数据，最后显式提交或回滚；DBMS 在此过程中记录日志、协调锁、控制版本可见性。

## 17.2 一个简单的事务模型

为讨论方便，教材使用一个抽象化的读写模型。每个事务 $T_i$ 只由如下三类操作组成：

- $\text{read}(X)$：从数据库读取数据项 $X$ 到 $T_i$ 的局部变量；
- $\text{write}(X)$：把 $T_i$ 的局部变量写回 $X$；
- $\text{commit} / \text{abort}$：宣告事务成功结束或强制回滚。

事务的生命周期可以用状态图刻画：

<Mermaid value={`stateDiagram-v2
  [*] --> Active
  Active --> PartiallyCommitted: 最后一条语句执行完
  PartiallyCommitted --> Committed: 日志写盘成功
  PartiallyCommitted --> Failed: 崩溃 / 违反约束
  Active --> Failed: 显式 ROLLBACK
  Failed --> Aborted: 回滚完成
  Committed --> [*]
  Aborted --> [*]`} />

- **活动 (active)**：初始状态，可继续执行读写；
- **部分提交 (partially committed)**：最后一条语句执行完，但日志尚未持久化；
- **失败 (failed)**：因错误或用户回滚等原因不能继续；
- **中止 (aborted)**：已回滚完毕，可以选择重启 (restart) 或杀死 (kill)；
- **已提交 (committed)**：已成功持久化。

在这一简单模型下，事务的语义可以完全由**读集 (read set)** 与**写集 (write set)** 描述：读集是事务读过的所有数据项集合，写集是被修改过的数据项集合。冲突分析、并发控制乃至可串行化判定都建立在读写集之上。

我们进一步引入**调度 (schedule)** 的概念：给定一组事务 $\{T_1, T_2, \dots, T_n\}$，调度 $S$ 是这些事务全部操作的一个有序序列，同一事务内部的操作在 $S$ 中仍保持事务内顺序。若 $S$ 中每个事务的所有操作都连续排列，则称之为**串行调度 (serial schedule)**；否则为**并发调度 (concurrent schedule)**。可串行化判定的对象正是这样的调度。

## 17.3 存储器结构

理解事务需要区分不同层次的存储：

- **易失存储 (volatile storage)**：主存、CPU 缓存，掉电即丢失；
- **非易失存储 (nonvolatile storage)**：磁盘、SSD，可掉电保存，但可能因坏道而丢失；
- **稳定存储 (stable storage)**：理想化概念，永不丢失。工程上通过**磁盘镜像**、多副本、异地备份、纠删码等方式尽量逼近。

为保证持久性，事务的提交动作必须把足够的信息写入稳定存储（一般是日志）。这就是**先写日志 (Write-Ahead Logging, WAL)** 原则：

> 在把修改后的数据页写回磁盘之前，其对应的 UNDO 日志必须已经写盘；在事务被认为已提交之前，其 REDO 日志必须已经写盘。

WAL 使得数据页的写回可以**懒惰化**（buffer pool 中脏页允许延迟刷盘）而不损害正确性——因为只要日志已经稳定，任何丢失的更新都可以通过 REDO 重现。与之对应，未提交事务的更新即便已经被顺手刷到磁盘，也可以通过 UNDO 记录反向撤销。日志本身通常按**日志缓冲区 → 组提交 (group commit) → 顺序追加到日志文件**的路径写入，充分利用顺序 I/O。

## 17.4 事务的原子性和持久性

原子性和持久性通过**日志 (log)** + **恢复子系统 (recovery manager)** 联合实现。最典型的方案是 ARIES 家族：

- 每次修改数据前，写一条日志：`<T_i, X, V_{old}, V_{new}>`；
- 事务提交时写 `<T_i commit>`，并将其之前的所有日志刷盘；
- 崩溃恢复时按**分析 → REDO → UNDO** 三段处理：
  - 分析：扫描日志，确定崩溃时哪些事务正在活动；
  - REDO：从最早的脏页 LSN 开始，重做所有日志中的更新；
  - UNDO：对崩溃时仍活动的事务按日志反向撤销。

这样即便主存中的修改尚未写入数据页，只要日志已经稳定持久化，都可以在恢复时正确重放；反之，若事务未提交而系统崩溃，则可根据日志把所有已写入磁盘的中间结果撤销。

**日志记录格式** 至少包含以下字段：事务号 $T_i$、数据项标识 $X$、旧值 $V_{old}$、新值 $V_{new}$，此外还有 LSN (Log Sequence Number) 用于定位、prev-LSN 用于链式回溯、事务类型（begin/update/commit/abort）。为了减少 UNDO 日志的空间开销，ARIES 使用**物理逻辑日志 (physiological logging)**：在页内用逻辑操作（如 insert/delete/update 某个 slot），在页外用物理引用（页号 + slot 号）。

**检查点 (checkpoint)** 是加速恢复的关键：DBMS 周期性地把当前所有脏页刷盘并把活动事务表写入日志。恢复时只需从上一次检查点开始扫描，而非从最早的日志。**模糊检查点 (fuzzy checkpoint)** 允许在写检查点期间事务继续执行，进一步降低阻塞。

原子性还与**中止代价**紧密相关：若事务已修改大量数据，回滚需要按 UNDO 日志逐条还原。为了在长事务中降低中止代价，常见做法包括**保存点**（部分回滚）与**乐观并发控制**（先执行、提交时校验、失败重启）。

## 17.5 事务的隔离性

并发执行不受控会引发多种异常：

- **丢失更新 (lost update)**：$T_1$ 与 $T_2$ 同时读同一余额并各自修改后写回，其中一次更新被覆盖；
- **脏读 (dirty read)**：$T_1$ 读到了 $T_2$ 尚未提交的中间值，若 $T_2$ 后来回滚，$T_1$ 相当于读了不存在的数据；
- **不可重复读 (non-repeatable read)**：$T_1$ 在同一事务中两次读同一行，中间被 $T_2$ 提交的更新改变了结果；
- **幻读 (phantom read)**：$T_1$ 用相同谓词两次查询，中间被 $T_2$ 插入/删除的行改变了结果集；
- **写偏斜 (write skew)**：两个并发事务分别读同一集合，各自根据读到的数据做独立更新，联合起来破坏了不变式（快照隔离下才会出现）。

**串行调度 (serial schedule)** 显然不会出现上述问题，但吞吐率过低。目标是让并发调度产生与某个串行调度等价的结果——即**可串行化 (serializable)**。

用一个具体例子理解丢失更新：

```text
T1: read(A) = 100                          -- 读到 100
T2:                    read(A) = 100        -- 也读到 100
T1: write(A) = 100 - 20                     -- 写回 80
T2:                    write(A) = 100 + 50  -- 写回 150，T1 的更新丢失
```

若加入并发控制（如两阶段封锁），$T_2$ 的 read 会等待 $T_1$ 的写锁释放，从而看到 80 并写回 130，结果正确。可见并发控制不是可有可无，而是保证正确性的必要机制。

## 17.6 可串行化

给定一个包含 $T_1, \dots, T_n$ 的调度 $S$，若存在一个串行调度 $S'$，使得对任意初始数据库状态两者产生相同的最终状态，则 $S$ 称为**可串行化**的。

工程上最常用的判定是**冲突可串行化 (conflict serializability)**：

- 若两条操作满足：属于**不同事务**、访问**同一数据项**且**至少一个是写**，则称它们**冲突**；
- 若可以通过交换**不冲突**的相邻操作，把 $S$ 转化为某个串行调度，则 $S$ 冲突可串行化。

用**优先图 (precedence graph)** 判定：对每个事务建一个结点；若 $S$ 中 $T_i$ 的某操作先于 $T_j$ 的冲突操作出现，则加边 $T_i \to T_j$。$S$ 冲突可串行化当且仅当该图**无环**，此时任一拓扑序即为等价的串行调度。

**示例：** 三个事务，调度片段如下（$r, w$ 表示读写）：

```
T1: r(A) w(A)
T2: r(A) w(A) r(B) w(B)
T3:              r(B) w(B)
```

顺序执行为 `r1(A) r2(A) w1(A) w2(A) r2(B) r3(B) w2(B) w3(B)`。

- $r_1(A)$ 与 $w_2(A)$ 冲突 → $T_1 \to T_2$；
- $r_2(A)$ 与 $w_1(A)$ 冲突 → $T_2 \to T_1$。

优先图存在环 $T_1 \leftrightarrow T_2$，故该调度**不是冲突可串行化**。

若把 $r_1(A)$ 与 $r_2(A)$ 的顺序调整，使得 $T_1$ 的所有操作都排在 $T_2$ 前，则得到等价的串行序 $T_1, T_2, T_3$，优先图无环。

除了冲突可串行化，还有更宽松的**视图可串行化 (view serializability)**：只要求每个事务在两种调度中读到的值一致、最终写入一致，不要求冲突序相同。视图可串行化包含冲突可串行化，但其判定为 NP 完全，实际系统仍以冲突可串行化为主。

值得注意的是，冲突可串行化只保证与**某个**串行调度等价，并不保证与真实时间上事务提交的顺序一致。若应用还要求"若 $T_1$ 在真实时间上先于 $T_2$ 提交，则等价的串行序中 $T_1$ 也应在 $T_2$ 之前"，则称调度是**严格可串行化 (strict serializable)** 的，这是分布式系统一致性讨论中的核心概念。

## 17.7 事务的隔离性和原子性

即便调度可串行化，也未必能容忍任意故障。要与原子性配合，还需引入两类更强的调度性质。

### 17.7.1 可恢复调度

若 $T_j$ 读到了 $T_i$ 写入的数据，则 $T_i$ 必须**先于** $T_j$ 提交。否则一旦 $T_i$ 回滚，$T_j$ 已经提交却依赖了被撤销的值，无法通过回滚 $T_j$ 修复。满足这一条件的调度称为**可恢复的 (recoverable)**。

### 17.7.2 无级联调度

**级联回滚 (cascading rollback)** 指一个事务的回滚触发一连串依赖它的事务的回滚。若限制"事务只能读已提交的数据"，则杜绝级联回滚，称调度**无级联 (cascadeless)**：无级联 ⊊ 可恢复 ⊊ 所有调度。

进一步，若要求事务对每个数据项的写入直到事务结束都不被其他事务读取或覆盖，则称调度**严格 (strict)**。严格调度下，恢复模块只需保留每个数据项的一个"提交前值"即可完成 UNDO，实现最为简单。严格两阶段封锁 (S2PL) 生成的调度即为严格调度。

三种性质的强弱关系为：

$$
\text{strict} \subset \text{cascadeless} \subset \text{recoverable} \subset \text{all schedules}
$$

主流商业数据库几乎都保证严格性；只有在极端追求并发度的场景下才会放宽到无级联。

## 17.8 事务的隔离性级别

由于严格可串行化的代价较高，SQL 标准允许应用在**隔离性级别**上做权衡：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 写偏斜 |
| --- | :---: | :---: | :---: | :---: |
| READ UNCOMMITTED（读未提交） | 可能 | 可能 | 可能 | 可能 |
| READ COMMITTED（读已提交） | 否 | 可能 | 可能 | 可能 |
| REPEATABLE READ（可重复读） | 否 | 否 | 可能* | 可能 |
| SERIALIZABLE（串行化） | 否 | 否 | 否 | 否 |

其中"可能*"取决于实现：SQL 标准允许 REPEATABLE READ 出现幻读；PostgreSQL 的 REPEATABLE READ 基于快照隔离，能防幻读但仍可能出现写偏斜；MySQL InnoDB 的 REPEATABLE READ 通过间隙锁 (gap lock) 阻止幻读。

隔离级别越高，并发度越低。应用应根据业务需求（读多写少 / OLTP / 报表）选择合适级别。

**选择示例**：

- **报表 / OLAP**：查询长、只读，选择 `READ COMMITTED` 或 `REPEATABLE READ` 即可，避免长时间锁定影响业务；PostgreSQL 常用 `REPEATABLE READ`，因为它基于快照隔离，不会加读锁。
- **在线交易 (OLTP)**：短事务频繁写入，默认 `READ COMMITTED` 通常足够；关键金额计算（如转账、账户扣减）应显式提升为 `SERIALIZABLE` 或加行锁 (`SELECT ... FOR UPDATE`)。
- **库存扣减**：典型的写偏斜场景，若使用 SI 级别需要 `SELECT ... FOR UPDATE` 或 SSI 才能保证不超卖。

调整隔离级别是**每事务粒度**的：不同事务可以使用不同级别，DBMS 会为每个事务独立配置并发控制策略。

## 17.9 隔离性级别的实现

### 17.9.1 锁

**两阶段封锁 (2PL, Two-Phase Locking)** 是保证冲突可串行化的经典协议：

- 事务分为**增长阶段 (growing)** 与 **收缩阶段 (shrinking)**：一旦释放任何一把锁，就不能再申请新锁；
- 若在收缩阶段之前保持所有锁到事务结束，称**严格两阶段封锁 (S2PL)**，既保证可串行化又杜绝级联回滚。

锁的两种基本模式：

- **共享锁 (S, shared)**：允许并发读；
- **排它锁 (X, exclusive)**：唯一写。

相容矩阵：

| 请求 \ 已持有 | S | X |
| --- | :---: | :---: |
| S | 相容 | 冲突 |
| X | 冲突 | 冲突 |

死锁在锁协议下不可避免，常用**等待图 (wait-for graph)** 检测或**超时 + 回滚**处理；也可使用**wait-die / wound-wait** 等预防策略。

- **wait-die**：老事务等待、年轻事务被回滚（非抢占）；
- **wound-wait**：老事务抢占年轻事务、年轻事务等待（抢占）。

对**幻读**的防护，共享/排它锁在行级别是不够的：新插入的行不存在于当前锁保护范围。解决办法有两种：**谓词锁 (predicate lock)** 锁住整个谓词范围，实现复杂但语义清晰；**间隙锁 (gap lock)** 锁住索引项之间的空隙，代价低但仅在有索引时有效。MySQL InnoDB 采用间隙锁 + 记录锁的组合，称为 **next-key lock**。

**多粒度封锁 (multiple granularity locking)** 允许在表级、页级、行级不同层次加锁，配合**意向锁 (IS, IX, SIX)** 声明高层意图：

- **IS (intent-shared)**：将对某后代加共享锁；
- **IX (intent-exclusive)**：将对某后代加排它锁；
- **SIX**：本层加共享锁 + 声明将对后代加排它锁。

意向锁兼容矩阵允许同层多个 IS/IX 并存，仅在真正加 X 时冲突，从而显著提升并发度。

### 17.9.2 时间戳

**时间戳协议 (timestamp ordering)** 为每个事务分配唯一时间戳 $\text{TS}(T)$，并按时间戳顺序决定读写：

- 若 $T$ 试图读 $X$，且 $\text{W-TS}(X) > \text{TS}(T)$，则 $T$ 回滚；
- 若 $T$ 试图写 $X$，且 $\text{R-TS}(X) > \text{TS}(T)$ 或 $\text{W-TS}(X) > \text{TS}(T)$，则 $T$ 回滚。

时间戳协议无死锁，但**饥饿**可能出现，且回滚代价可能较大。

### 17.9.3 多版本和快照隔离

现代数据库（PostgreSQL、Oracle、SQL Server、MySQL InnoDB）广泛采用**多版本并发控制 (MVCC)**：

- 每条数据保留多个版本，每个版本带写入事务的时间戳；
- 读事务读取自己开始时刻能看到的版本，**读不加锁**；
- 写事务写新版本，冲突检测在提交时进行。

**快照隔离 (Snapshot Isolation, SI)**：事务读到的是启动时刻的数据库快照，杜绝脏读、不可重复读，几乎防幻读；但存在**写偏斜**——两事务并发写不同项却同时依赖对方的读，产生联合不变式破坏。**可串行化快照隔离 (SSI)** 通过检测读写依赖环进一步保证严格可串行化，PostgreSQL 的 SERIALIZABLE 即基于 SSI 实现。

**写偏斜示例**：值班表规则"至少要有一位医生 on-call"。$T_1, T_2$ 是两位医生同时申请下班：

```text
T1: SELECT count(*) FROM oncall WHERE working = true;   -- 读到 2
T1: UPDATE oncall SET working = false WHERE name='A';
T2: SELECT count(*) FROM oncall WHERE working = true;   -- 快照下读到 2
T2: UPDATE oncall SET working = false WHERE name='B';
COMMIT (both)
```

两个事务都基于"还有 2 人 on-call"的读结果各自把一人置为下班，SI 检查不到冲突（写集不相交），但联合起来违反了"至少一人 on-call"的语义。SSI 则维护每个事务的**读依赖图**，检测到 $T_1, T_2$ 存在 rw-antidependency 环时会强制回滚其中之一，避免此类异常。

MVCC 相比锁的优势：读写互不阻塞、只读事务几乎无开销。代价则是需要**版本清理 (vacuum)**：过时版本必须定期回收，否则表膨胀（bloat）严重。PostgreSQL 的 auto-vacuum、MySQL 的 purge 线程都承担这一角色。

## 17.10 事务的SQL语句表示

标准 SQL 提供了显式的事务控制语句。以 PostgreSQL 为例：

```sql
-- 显式开启事务，并指定隔离级别
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 业务操作
UPDATE account SET balance = balance - 100 WHERE id = 'A';

-- 设置保存点，允许部分回滚
SAVEPOINT sp1;
UPDATE account SET balance = balance + 100 WHERE id = 'B';

-- 若 B 账户操作失败，只回滚到 sp1，A 的更新仍保留在事务中
ROLLBACK TO SAVEPOINT sp1;

-- 重新执行修正后的操作
UPDATE account SET balance = balance + 100 WHERE id = 'C';

COMMIT;   -- 或 ROLLBACK;
```

主要语句语义：

- `BEGIN` / `START TRANSACTION`：显式开启事务，之后自动关闭 autocommit。
- `SET TRANSACTION ISOLATION LEVEL {READ UNCOMMITTED | READ COMMITTED | REPEATABLE READ | SERIALIZABLE}`：为当前事务指定隔离级别，必须紧随 `BEGIN` 之后。
- `SAVEPOINT sp`：保存点，允许在同一事务内部分回滚。
- `ROLLBACK TO SAVEPOINT sp`：回滚到保存点之后释放该保存点之后的所有子操作；事务本身仍未结束。
- `RELEASE SAVEPOINT sp`：显式释放保存点。
- `COMMIT`：提交事务，效果永久生效。
- `ROLLBACK`：撤销事务全部操作。
- `SET TRANSACTION READ ONLY`：声明只读，优化器可跳过锁与版本管理。

自动提交模式 (auto-commit)：默认情况下每条语句独立成事务。JDBC/ODBC 中可通过 `setAutoCommit(false)` 关闭。分布式事务则用 `XA` 接口（`XA START`, `XA END`, `XA PREPARE`, `XA COMMIT`）与两阶段提交协议协调。

在应用编程中，事务边界常与**连接池**的行为耦合：应用从连接池获取连接、开启事务、执行 SQL、提交/回滚、归还连接。若忘记显式提交或回滚，即使连接归还连接池，事务也可能保留在活动状态，导致锁泄漏。为此，Java 的 `try-with-resources`、Python 的 `with conn:` 上下文管理器等语言级机制被广泛推荐使用，示例：

```python
import psycopg2
with psycopg2.connect(DSN) as conn:      # 事务范围与 with 块绑定
    with conn.cursor() as cur:
        cur.execute("UPDATE account SET balance = balance - 100 WHERE id='A'")
        cur.execute("UPDATE account SET balance = balance + 100 WHERE id='B'")
    # 正常退出自动 COMMIT，异常自动 ROLLBACK
```

在框架层面，Spring 的 `@Transactional`、SQLAlchemy 的 `Session`、Django 的 `atomic()` 都进一步把事务边界与请求 / 业务方法绑定，从而降低漏提交、漏回滚的概率。

分布式场景下需要跨多个资源管理器（RM）保证原子性，此时使用**两阶段提交 (2PC)**：

1. **准备 (prepare) 阶段**：协调者向所有参与者发送 prepare，参与者写入 prepared 日志并回复 yes/no；
2. **提交 (commit) 阶段**：协调者收集响应，若全部 yes 则广播 commit，否则广播 abort；参与者按协调者决定完成本地提交或回滚。

2PC 保证原子性但是阻塞式协议——协调者故障时参与者会一直等待。三阶段提交 (3PC)、Paxos-Commit 等改进被提出以增强可用性，但工程上仍以 2PC 与基于共识的复制状态机（Raft/Paxos）居多。

## 17.11 总结

- 事务是数据库的最小执行单元，用 ACID 概括其应满足的四条性质。
- 原子性与持久性靠日志 + 恢复子系统（如 ARIES）实现；隔离性靠并发控制协议实现；一致性依赖应用与约束。
- 并发异常主要有脏读、不可重复读、幻读、写偏斜；SQL 标准据此定义四个隔离级别，级别与性能存在权衡。
- 冲突可串行化用优先图判定；两阶段封锁、时间戳排序、多版本并发控制是三大主流并发控制协议。
- 现代数据库多采用 MVCC 与快照隔离，PostgreSQL 的 SSI 在此基础上进一步逼近串行化。
- SQL 提供 `BEGIN` / `COMMIT` / `ROLLBACK` / `SAVEPOINT` / `SET TRANSACTION ISOLATION LEVEL` 等语句显式控制事务边界与隔离级别，是编写正确并发程序的基础工具。

**知识要点自查表**：

| 主题 | 关键概念 | 主要机制 / 公式 |
| --- | --- | --- |
| 原子性 | 全做或全不做 | UNDO 日志、事务回滚、检查点 |
| 一致性 | 从合法态到合法态 | 应用逻辑 + 约束（PK/FK/CHECK） |
| 隔离性 | 并发等价于某种串行 | 2PL、时间戳、MVCC、SSI |
| 持久性 | 提交后永久保存 | WAL、REDO 日志、稳定存储 |
| 冲突可串行化 | 无环优先图 | 拓扑排序得等价串行序 |
| 隔离级别 | 4 档 vs 4 类异常 | READ UNCOMMITTED → SERIALIZABLE |
| 死锁 | 等待图有环 | 检测回滚 or wait-die/wound-wait |
| 多粒度锁 | IS/IX/S/X/SIX | 意向锁兼容矩阵 |
| MVCC | 版本时间戳 | 读快照、写冲突检测、vacuum |
| 事务 SQL | 事务边界控制 | BEGIN / COMMIT / ROLLBACK / SAVEPOINT |

**常见误区**：

1. "把 `SELECT` 用在事务外就是安全的" —— 错。若涉及多条相关查询（如汇总 + 计数），仍应在同一事务中读取，否则可能得到不一致视图。
2. "SERIALIZABLE 就一定慢" —— 不一定。PostgreSQL 的 SSI 是乐观的，冲突少时开销很小；只有真正的写冲突才回滚。
3. "AUTO COMMIT 关掉后不显式 COMMIT 也不影响" —— 错。未提交事务会一直持有锁与版本，最终会阻塞其他事务或撑爆版本存储。
4. "REPEATABLE READ 一定能防幻读" —— 视实现而定：SQL 标准允许幻读，PostgreSQL SI 通常防幻读但仍有写偏斜，MySQL InnoDB 通过 next-key lock 完全防幻读。
5. "写日志比写数据慢" —— 相反：日志是顺序追加，通常比随机写数据页快一个数量级。这正是 WAL 能显著提升吞吐的原因。

理解事务的四条性质以及为实现它们付出的机制代价，是设计高性能数据库应用的前提，也是从"能写 SQL"到"能诊断并发问题"的关键跨越。
