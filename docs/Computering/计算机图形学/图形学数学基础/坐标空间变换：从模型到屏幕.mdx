# 坐标空间变换：从模型到屏幕

一个三角形顶点从美术软件里被建出来,到出现在你显示器的某个像素上,中间要经过至少五次坐标变换。**每次变换都对应一个矩阵,每个空间都有明确的物理意义**。不理解这条链路,写着色器时会不知道当前顶点在哪个空间、法线该怎么变、深度值为何长成那样。

这一篇顺着变换链路走一遍,重点在**为什么要有这些空间**——不是数学游戏,而是硬件、艺术、性能三方妥协的产物。前置知识见[向量与矩阵](./向量与矩阵：图形学的数学基石.mdx)。

## 1. 空间的全景图

```
模型空间 ──M──> 世界空间 ──V──> 视图空间 ──P──> 裁剪空间 ──/w──> NDC ──视口──> 屏幕
(Object)       (World)         (View/Eye)     (Clip)          (Normalized)  (Screen)
```

- **M**:模型矩阵,由物体的位置、旋转、缩放构成
- **V**:视图矩阵,由相机位姿的逆构成
- **P**:投影矩阵,把视锥体压成立方体
- **/w**:透视除法,由 GPU 硬件自动做
- **视口变换**:把 $[-1,1]^3$ 拉到屏幕分辨率

顶点着色器输出的 `gl_Position` 就在**裁剪空间**——之后的裁剪、透视除法、视口变换、光栅化都是硬件负责。你写 shader 只操心从模型到裁剪这一段。

## 2. 齐次坐标:平移与投影的通用语

三维点写成 $(x,y,z,1)$、方向写成 $(x,y,z,0)$ 的动机在[向量与矩阵](./向量与矩阵：图形学的数学基石.mdx)里已经解释——把平移线性化。但齐次坐标真正的威力在**投影**:

$$
(x,y,z,w) \sim (kx,ky,kz,kw), \quad k\neq 0
$$

同一条从原点出发的射线上的所有点被视作等价——这是**射影几何**的基本对象"射影点"。透视投影产生的顶点 $w$ 不再是 1,除以 $w$ 相当于把射线交到 $w=1$ 平面上,几何上就是"过焦点向图像平面投影"。

一个三维空间里的直线,在投影后仍然是直线;两条平行线在射影空间里交于**无穷远点**(方向向量,$w=0$)——这就是绘画里的"消失点"的数学根源。

## 3. 模型空间与模型矩阵

美术在 Blender/Maya 里建模时,模型有自己的原点、朝向、单位。这个坐标系叫**模型空间**(也叫 object space、local space)。角色的脚在原点、头朝 +Y、正面朝 +Z,是典型约定。

模型矩阵 $M$ 把模型空间的顶点搬到**世界空间**——一个所有物体共享的坐标系。一般由平移、旋转、缩放三个矩阵组合:

$$
M = T\cdot R\cdot S
$$

顺序不能变:先缩放(在自己坐标系里放大),再旋转(绕自己原点转),最后平移(移到世界某处)。缩放放在最右,是因为缩放操作应该发生在物体的**局部坐标系**里,不能被之前的旋转干扰。

**层次结构**:游戏引擎里父物体的变换会作用到子物体上,子物体的世界矩阵 $M_{\text{子}}^{\text{世界}} = M_{\text{父}}^{\text{世界}}\cdot M_{\text{子}}^{\text{局部}}$。角色的手在角色空间里的位置乘以角色的世界矩阵才是手在世界里的位置。骨骼动画的 shader 里 `boneMatrix` 就是这么一层层组合出来的。

### 3.1 法线变换的陷阱

顶点用 $M$ 变换,法线**不能直接用 $M$**。如果 $M$ 里有非均匀缩放(比如 $S=\text{diag}(2,1,1)$),法线原本垂直于表面,乘以 $M$ 后会歪。正确的法线矩阵是 $(M^{-1})^T$——见[向量与矩阵](./向量与矩阵：图形学的数学基石.mdx)第 5 节的推导。

如果 $M$ 只含旋转和均匀缩放,$(M^{-1})^T=M/s^2$,和 $M$ 差一个比例因子,单位化后不影响方向。这就是很多教程说"法线用左上 3x3 就行"的前提条件——但一旦有非均匀缩放,这个近似就崩了。工程上要么禁止非均匀缩放,要么老实算法线矩阵传进 shader。

## 4. 视图空间:把相机放到原点

**世界空间**里相机可以在任何位置任何朝向。为了简化后续投影,把相机搬到原点、看向 $-Z$、上方向为 $+Y$——这个空间叫**视图空间**(view/eye/camera space)。视图矩阵 $V$ 就是把世界变换到这个坐标系的矩阵。

物理上,$V$ 是相机在世界里的变换 $M_{\text{cam}}$ 的**逆**:

$$
V = M_{\text{cam}}^{-1}
$$

因为相机在世界里的位姿等价于"世界相对相机反向移动"。相机往右走 = 世界往左走。

`gluLookAt(eye, target, up)` 构造 $V$ 的过程在[向量与矩阵](./向量与矩阵：图形学的数学基石.mdx)第 7 节展开过。核心是构造三个正交基向量 $r,u,f$,再拼上 $-\vec{e}$ 平移。

### 4.1 左手还是右手

OpenGL 视图空间是右手系,相机看向 $-Z$。DirectX 是左手系,相机看向 $+Z$。区别只影响投影矩阵中间几个符号,但跨 API 移植时经常翻车。Unity 内部用左手,着色器用右手——Unity 帮你自动转,自己写的时候要小心。

判断技巧:右手四指从 $+X$ 弯向 $+Y$,拇指指 $+Z$ 就是右手系。

## 5. 投影:把视锥变成立方体

视图空间里,相机能看到的区域是一个**视锥体**(frustum)——正面被近裁剪面 $n$ 截断,背面被远裁剪面 $f$ 截断,侧面被视场角限定。GPU 硬件光栅化只对**规则的立方体** $[-1,1]^3$ 感兴趣,所以要有一个变换把视锥压成立方体。这就是投影矩阵。

### 5.1 正交投影

视锥就是一个长方体,投影矩阵只做拉伸平移:

$$
P_{\text{ortho}} = \begin{bmatrix}\frac{2}{r-l}&0&0&-\frac{r+l}{r-l}\\0&\frac{2}{t-b}&0&-\frac{t+b}{t-b}\\0&0&-\frac{2}{f-n}&-\frac{f+n}{f-n}\\0&0&0&1\end{bmatrix}
$$

平行线保持平行,没有近大远小。CAD、UI、2D 游戏、阴影贴图(定向光)都用正交。

### 5.2 透视投影

透视是**近大远小**——远的物体在屏幕上更小。数学上是"除以 $z$"。齐次坐标让这件事变成线性变换:

$$
P_{\text{persp}} = \begin{bmatrix}\frac{n}{r}&0&0&0\\0&\frac{n}{t}&0&0\\0&0&-\frac{f+n}{f-n}&-\frac{2fn}{f-n}\\0&0&-1&0\end{bmatrix}
$$

(对称视锥,$r=-l,t=-b$;非对称视锥略有不同。)

关键在**第四行**:$(0,0,-1,0)$。它让输出的 $w=-z_{\text{view}}$。裁剪空间坐标除以 $w$ 就变成了"$x/(-z)$"——正是近大远小的公式。

**投影矩阵的作用是把视锥内的一切非线性映射到 $[-1,1]^3$**——$x$ 和 $y$ 除以深度以模拟透视,$z$ 被非线性重映射到 $[-1,1]$。这个非线性正是深度精度问题的根源。

### 5.3 深度精度:为什么近裁剪面不能太小

投影矩阵作用后深度的非线性:

$$
z_{\text{ndc}} = \frac{f+n}{f-n} + \frac{-2fn}{(f-n)z_{\text{view}}}
$$

$z_{\text{ndc}}$ 是关于 $1/z_{\text{view}}$ 的线性函数。这意味着**接近近裁剪面的地方精度极高,接近远裁剪面的地方精度极低**。经验数据:$n=0.1,f=1000$ 时,90% 的深度缓冲精度都花在了前 10 米,后面几百米挤在一起,导致 z-fighting。

工程对策:

- 尽量提高 $n$。$n=1$ 而不是 $0.01$。
- 缩小 $f$。开放世界大地图会做多层视锥(cascade)。
- **反向 Z**(reversed-Z):近处映射到 1、远处映射到 0,配合浮点深度缓冲,把浮点精度密集区(近 0 处)分配给远处,极大改善精度。现代 AAA 引擎标配。
- **对数深度缓冲**(logarithmic depth):牺牲一点 shader 开销换极大深度范围,行星级渲染用。

## 6. 裁剪空间与齐次裁剪

投影矩阵作用后,顶点在**裁剪空间**——齐次坐标 $(x_c,y_c,z_c,w_c)$。GPU 硬件在这里做裁剪:判断顶点是否满足 $-w\leq x\leq w$、$-w\leq y\leq w$、$-w\leq z\leq w$。三个不等式定义了一个立方体,裁剪掉外面的部分。

**为什么要在齐次坐标里做裁剪,而不是先除以 $w$ 再裁剪**?

因为 $w$ 可能是负的——当顶点在相机后面时,$w=-z_{\text{view}}<0$。除以负数会翻转不等号方向,让本该在视锥外的顶点"看起来"在视锥内,产生神秘的"图元穿过相机后面反着显示"的 bug。齐次裁剪先剔除 $w\leq 0$ 的部分,再做正数除法。

裁剪产生的新顶点由 Sutherland-Hodgman 算法在每条边上按平面参数插值得到,顶点属性(法线、UV、颜色)也要相应插值——这一步硬件透明处理,shader 感知不到,但**属性插值是否透视校正**决定了纹理会不会变形。

## 7. 透视除法与 NDC

裁剪之后,GPU 做**透视除法**:

$$
(x_{\text{ndc}},y_{\text{ndc}},z_{\text{ndc}}) = (x_c/w_c, y_c/w_c, z_c/w_c)
$$

结果落在 $[-1,1]^3$,称为**归一化设备坐标**(Normalized Device Coordinates, NDC)。这个立方体是一切图形硬件的"统一战场"——不管你用什么投影、什么视锥,来到 NDC 就都是同一个立方体。

NDC 有一个"约定差异":

- OpenGL:$z_{\text{ndc}}\in[-1,1]$
- DirectX/Vulkan/Metal:$z_{\text{ndc}}\in[0,1]$

后者精度更优(负半段是浪费),所以 Vulkan 和 D3D 都选了这个。OpenGL 4.5 之后也支持 `glClipControl` 切换。

## 8. 视口变换:落到屏幕像素

最后一步:

$$
x_{\text{screen}} = \frac{x_{\text{ndc}}+1}{2}\cdot W + O_x
$$
$$
y_{\text{screen}} = \frac{y_{\text{ndc}}+1}{2}\cdot H + O_y
$$

$W,H$ 是视口宽高,$O_x,O_y$ 是视口左下角(OpenGL)或左上角(DirectX)的屏幕坐标。

**y 轴翻转**又是一个 API 差异:OpenGL 屏幕原点在左下,DirectX 在左上。跨引擎渲染纹理(FBO)时经常上下颠倒,就是这里。

$z_{\text{screen}}$ 常映射到 $[0,1]$,写入深度缓冲,后面的深度测试用它。

## 9. 一个具体的例子:顶点着色器里发生了什么

标准顶点着色器:

```glsl
uniform mat4 uModel, uView, uProj;
in vec3 aPos;
in vec3 aNormal;
out vec3 vWorldPos;
out vec3 vNormal;

void main() {
    vec4 worldPos = uModel * vec4(aPos, 1.0);
    vWorldPos = worldPos.xyz;
    vNormal = mat3(transpose(inverse(uModel))) * aNormal;
    gl_Position = uProj * uView * worldPos;
}
```

三行代码分别对应:

1. 模型空间 → 世界空间(位置)
2. 传出世界坐标供片元 shader 做光照
3. 世界 → 视图 → 裁剪空间

`gl_Position` 输出后 GPU 接管:齐次裁剪 → 透视除法 → 视口 → 光栅化 → 片元 shader。整个链路里 shader 只写第 1 到第 3 行。

## 10. 属性插值与透视校正

光栅化时,每个像素的属性(UV、法线、颜色)从三个顶点插值而来。**朴素的重心坐标插值在屏幕空间是错的**——透视变换后,直线仍是直线但等分点不再是等分点。举例:一条水平铁轨的两根枕木,近的枕木在屏幕上占 20 像素,远的占 5 像素。屏幕上的中点对应的 3D 空间点不是铁轨的中点。

解决办法是**透视校正插值**:插值 $1/w$ 和 $\text{attr}/w$,再做除法:

$$
\text{attr}_{\text{correct}} = \frac{\sum \lambda_i \text{attr}_i/w_i}{\sum \lambda_i/w_i}
$$

GPU 硬件默认开启,GLSL 里 `noperspective` 关键字可以强制关闭(极少数场景需要,如后处理特效)。

## 11. 逆变换:从屏幕反推到世界

拾取(鼠标点击场景里的物体)、屏幕空间射线追踪等场景需要**从屏幕坐标反推世界坐标**。链路:

$$
\text{screen} \xrightarrow{V^{-1}_{\text{viewport}}} \text{NDC} \xrightarrow{\times w} \text{clip} \xrightarrow{P^{-1}} \text{view} \xrightarrow{V^{-1}} \text{world}
$$

有个陷阱:NDC → 裁剪要乘以 $w$,而 $w$ 未知。做法是**指定深度**(比如 $z_{\text{ndc}}=0$ 代表近平面、$1$ 代表远平面),得到近点和远点各一个,连线就是屏幕像素对应的世界射线。这个射线送给[光线追踪](../光线追踪/光线追踪基本原理.mdx)或物理引擎做拾取。

## 12. 变换链路的性能常识

- 模型矩阵、视图矩阵在 CPU 端预乘为 `uModelView`,shader 里只做一次乘法
- `uView * uProj` 一起预乘为 `uViewProj`,常在 uniform buffer 里
- 大量物体的 `uModel` 用 SSBO/UBO 批量存,配合 instancing
- 蒙皮矩阵每帧更新,几十到几百个 4x4,通常打包成骨骼纹理或 SSBO
- 4x4 矩阵有 16 float = 64 字节,uniform buffer 对齐要求 16 字节倍数,天然吻合

不到必要不要在 shader 里做矩阵求逆——`inverse(mat4)` 在 GLSL 里编译出的指令数可怕。CPU 端算好传进来。
