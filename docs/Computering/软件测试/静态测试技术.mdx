# 静态测试技术：不跑代码就找 bug

静态测试（static testing）是"不执行程序就找问题"的方法总称。它比动态测试早、比动态测试便宜、比动态测试稳。核心逻辑就一句话：越晚发现 bug 越贵，所以能在敲下回车之前抓到就别等到运行时。

## 1. 什么是静态测试

静态测试对着代码本身找问题：读它、扫描它、类型系统推理、抽象解释、模式匹配。它不需要你写测试用例，也不需要把程序跑起来。

它和 [白盒测试](./动态测试：白盒测试.mdx)、[黑盒测试](./动态测试：黑盒测试.mdx) 的分界线是**要不要执行代码**。动态测试要构造输入、跑程序、看输出；静态测试连编译都不一定需要——Linter 通常只解析 AST 就够了。

静态测试涵盖两大类：

- 人工方法：代码走查（walkthrough）、代码评审（code review）、正式审查（inspection，Fagan 那套）
- 自动方法：Linter、类型检查、静态分析、符号执行、抽象解释

人工方法抓的是"这段代码写得不对（业务、可读性、架构）"，机器抓的是"这段代码违反某种可枚举规则"。两者互补，谁也代替不了谁。

## 2. 为什么静态早、便宜、有效

软件工程里被引到烂的一张图是 Boehm 的"缺陷发现成本曲线"：

| 阶段 | 相对修复成本 |
|---|---|
| 需求 / 设计 | 1x |
| 编码 | ~5x |
| 单元测试 | ~10x |
| 集成 / 系统测试 | ~20x |
| 上线后 | 100–1000x |

数字后来 Capers Jones 也提过修正版本，绝对值有争议，但曲线方向不动摇：越晚越贵，且是数量级式变贵。原因不是"技术上难修"，而是回归代价堆积——一个 bug 到生产才发现，你要复现、走事故流程、写 postmortem、通知用户，可能触发数据回滚。

静态测试卡在最左边。IDE 打字时红波浪线亮起就相当于 1x 阶段修复。这个价值不是"多找 bug"，而是**把发现时机往前推**。你不会因为 ESLint 变得更聪明，但你会因为它省下的返工时间成为一个更快的工程师。

再一个理由：静态测试的覆盖是**穷尽的**。动态测试只能覆盖你实际跑过的路径，100% 覆盖率也只是"我构造的用例都跑到了"。静态分析对源码文件全量扫描——只要规则命中，一个都跑不掉。

## 3. 人工审查

先说人工的，因为它是所有静态方法的爷爷。1976 年 Michael Fagan 在 IBM 提出的 Inspection 流程有 6 步：Planning、Overview、Preparation、Meeting、Rework、Follow-up。核心是"多人独立读、然后开会对齐"。

现代团队没人真跑 Fagan 全套，但 code review（GitHub PR、Gerrit）本质上就是它的轻量版：作者写完 → reviewer 独立读 → 留 comment → 作者改 → re-review。

轻量 code review 抓到的 bug 类型和静态分析工具重合度很低：

| 抓什么 | Reviewer | Linter / 静态分析 |
|---|---|---|
| 命名、可读性 | ✓ | 部分（长度规则） |
| 业务逻辑错误 | ✓ | ✗ |
| 架构 / 分层违规 | ✓ | 部分（ArchUnit 类） |
| 并发 / 时序 bug | 部分 | 部分（TSan） |
| 空指针 / 资源泄漏 | 部分 | ✓ |
| 代码风格 | ✗（人不该干这个） | ✓ |
| API 误用 | 部分 | ✓ |

工业界的通行做法是：**Linter 先跑一遍把风格问题清干净，reviewer 只看逻辑**。别让人肉去数缩进和逗号，那是浪费。

## 4. Linter

Linter 是最轻量的一档静态分析：解析 AST、规则匹配、报告违规。它不做深度数据流分析，也不做符号执行。速度快、误报少、集成简单。

各语言的主流 Linter：

| 工具 | 语言 | 规则数 | 特色 |
|---|---|---|---|
| ESLint | JS/TS | 200+ 内置 + 生态插件 | 可插拔，typescript-eslint 支持类型感知规则 |
| Pylint | Python | 400+ | 严格出名，误报也多 |
| Ruff | Python | 700+ | Rust 写的，速度是 Pylint 的 10–100 倍 |
| golangci-lint | Go | 聚合 60+ 个 linter | 官方推荐组合拳 |
| Clippy | Rust | 700+ | cargo 内置，几乎标配 |
| RuboCop | Ruby | 400+ | 也管代码风格自动修复 |
| ktlint / detekt | Kotlin | 100+ / 200+ | 前者管风格，后者管代码坏味 |

Linter 抓到的典型问题：未使用变量、变量遮蔽、`==` vs `===`、缺少 return、不可达代码、误用 API（比如把 `Array.prototype.forEach` 当有返回值用）、圈复杂度过高。

一个具体的例子：

```js
// ESLint 的 no-shadow + no-redeclare 会亮红
function process(user) {
  const user = getUser(user.id);  // 遮蔽了参数
  return user.name;
}
```

这种 bug 一跑就能发现吗？不一定，因为函数可能因为动态调用不在测试路径上；就算跑到，如果 `getUser` 恰好也返回一个有 name 的对象，测试还会通过。静态分析在这里的价值是"完全不看运行时也知道你写错了"。

## 5. 静态分析

静态分析比 Linter 深一档：不光看语法，还要做数据流、控制流、类型推导。它能回答"这个变量到这里可能是 null 吗"、"这段内存哪里释放"、"这个锁在所有路径上都释放了吗"。

工业界几个代表：

| 工具 | 主打 | 技术路线 |
|---|---|---|
| SonarQube | 全语言、企业级 | 数据流 + 规则库 + 度量 |
| Semgrep | 模式匹配 | AST 模式语法，写规则像写代码 |
| CodeQL | 深度查询 | 把代码当数据库，用 QL 语言查 |
| Coverity | C/C++/Java 大厂 | 过程间数据流、路径敏感 |
| Infer（Meta 开源） | 空指针、内存 | 基于 separation logic 的过程间分析 |
| SpotBugs | Java | 字节码级模式匹配 |
| clang-tidy | C/C++ | 基于 Clang AST |

Linter 和静态分析的分界：Linter 通常是**过程内、语法级**；静态分析常做**过程间、语义级**。ESLint 报"这里可能空指针"止步于当前函数，Infer 会跨函数追踪一个 `null` 从被返回到被解引用的整条路径。

举一个 Java 例子（SpotBugs 抓资源泄漏）：

```java
public String readFile(String path) throws IOException {
    FileInputStream in = new FileInputStream(path);
    byte[] buf = new byte[1024];
    in.read(buf);
    return new String(buf);
    // in 没 close，异常路径也没 close
}
```

SpotBugs 报 `OS_OPEN_STREAM`。这个 bug 大概率单元测试跑不出来——因为 JVM 短时间内不会耗尽 fd。等到线上跑一天崩了才发现，那就是 100x 修复成本了。

## 6. 类型检查

类型系统是"分类学式的静态分析"。它规定"这个值只能这么用"，编译器 / 检查器强制执行。

强类型语言（Rust、Haskell、OCaml）的类型检查本身就是一种静态测试——它保证的是**可枚举的一类 bug 永远不发生**：

- Rust 的 borrow checker：no data race、no use-after-free、no double-free
- Haskell 的类型：no null pointer（`Maybe` 强制处理）
- TypeScript 的 `strict`：no implicit any、no non-null assertion 漏网

对动态语言，类型检查是可选加装：TS 之于 JS、mypy / pyright 之于 Python、Sorbet 之于 Ruby。这些工具一旦全项目开启，抓到的 bug 密度极高——动态语言里"这个字段可能不存在"是家常便饭。

一个 Python 例子，mypy 直接报错：

```python
def greet(name: str) -> str:
    return "Hello, " + name

greet(None)  # error: Argument 1 to "greet" has incompatible type "None"; expected "str"
```

跑测试可能抓到，但只有你测试恰好传 `None`。类型检查是**所有调用点一起看**，覆盖完整。

## 7. 符号执行

符号执行走得更远：它不给变量赋具体值，而是给一个**符号**，然后按控制流走所有分支，收集路径约束，最后交给 SMT 求解器判断"这条路径可达吗、可达时有没有违规"。

伪代码：

```
function f(int x):
  if (x > 10):
    if (x < 5):
      crash()   // 符号执行发现约束 x>10 ∧ x<5 不可解，标为不可达
```

KLEE、angr、Z3 都是这个圈子的名字。KLEE 曾经跑了一遍 GNU coreutils，挖出了十几个多年没抓到的 bug——`echo`、`mkdir` 里的边界情况。

限制也很明显：**路径爆炸**。每个分支都要分叉，循环里 $n$ 次迭代分支就 $2^n$，实际系统的路径数轻松破亿。工业中符号执行往往只能对单函数或深度受限的调用图跑，跑不动整个应用。它更多是研究和高安全场景（内核、加密库、合约）的工具，不是日常 CI 的选项。

## 8. 抽象解释

比符号执行更"数学"的一支叫**抽象解释**（abstract interpretation）：不精确追踪具体值，而是把值域抽象成一个格（lattice）上的元素，然后计算不动点。

用人话讲：不算"x 具体等于什么"，只算"x 在 [-∞, 10] 这个范围里"。牺牲精度换可扩展性。

工业代表是 Astrée，法国 Airbus 用它证明飞控软件没有运行时错误（无溢出、无除零、无 UB）。这是**形式化验证**级别的静态分析，成本很高，只在航天、核电、汽车 ISO 26262 之类的地方才划得来。

抽象解释和符号执行对照：

| 维度 | 符号执行 | 抽象解释 |
|---|---|---|
| 精度 | 高（路径级） | 中（值域级） |
| 可扩展性 | 差（路径爆炸） | 好（收敛到不动点） |
| 误报 | 少 | 较多（过近似导致假阳） |
| 漏报 | 多（路径没跑到就漏） | 少（保守） |
| 典型场景 | 找具体 bug、漏洞挖掘 | 证明"永远不会崩" |

## 9. 局限

静态测试不是银弹。几个诚实的问题：

- **误报**：越强的分析越可能报"其实不会出问题的路径"，工程师久了会 alert fatigue，然后开始一律 suppress。SonarQube 项目里满屏 `NOSONAR` 就是这个原因。
- **动态特性无解**：反射、`eval`、字符串拼 SQL、跨服务 RPC——静态分析看不进去。这些必须靠 [模糊测试](./模糊测试.mdx)、[集成测试](./按粒度：测试层次.mdx)、[混沌工程](./混沌工程与弹性测试.mdx) 补上。
- **规则库依赖**：静态分析只能抓"已知模式"的 bug。逻辑正确性、业务错误它一无所知。
- **配置成本**：越强的工具越难上手。CodeQL 好用，但你要写 QL 查询；Coverity 精准，但企业授权和调优要专职人。

一句话：静态测试的作用是**把大量已知的低级 bug 挡在编译前**，让人力和动态测试的预算专注在真正需要人脑的部分。

## 10. 静态测试在测试家谱里的位置

往前追溯，静态测试是最古老的一档——早于 Fortran 写完就有人 desk-check。往后延伸，它和几乎所有其他测试互补：

- 与 [白盒测试](./动态测试：白盒测试.mdx)：白盒要跑代码，静态不用；两者覆盖的 bug 类型不重叠
- 与 [黑盒测试](./动态测试：黑盒测试.mdx)：黑盒只看接口，静态直接看实现
- 与 [自动化测试](./自动化测试.mdx)：静态分析是最容易自动化的部分——写规则一次跑万次
- 与 [变异测试](./变异测试.mdx)：变异测试检测"测试用例的强度"，静态分析检测"源码本身的缺陷"
- 与 [精准测试](./精准测试.mdx)：静态分析给出的调用图是精准测试做用例选取的输入
- 与 [测试过程与生命周期](./测试过程与生命周期.mdx)：静态测试最适合放在 pre-commit / CI 的最前端
- 与 [测试工具简介](./测试工具简介.mdx)：本文提到的工具几乎都在那份工具清单里出现

CI 流水线的经验顺序：**Linter → 类型检查 → 单元测试 → 集成测试 → 静态深度分析（夜间）**。前面几档几秒就跑完、失败率高、修复代价低；后面几档慢、贵、放在低频次运行。这个顺序对应的就是 Boehm 曲线——把便宜的挡板放在最前面。
