# 敏捷测试：把测试塞进 Sprint 里

敏捷测试（Agile Testing）想说的事情不复杂：如果开发已经从"一年一版"变成"两周一版"，测试还想守着"开发写完再交给我"的旧节奏，就一定跟不上。敏捷测试把"测试"从一个阶段拆散成一种活动，让它在整个 Sprint 里持续发生——需求、设计、编码、验收每一步都有测试的介入。Lisa Crispin 和 Janet Gregory 的 *Agile Testing* 那本书是这套方法论的教科书，测试四象限（Testing Quadrants）就出自她们。

## 1. 敏捷测试到底"敏捷"在哪

先给一个尽量准确的定义：敏捷测试是**在敏捷开发（Scrum、XP、Kanban 等）框架内，由整个团队共同负责质量的一套实践**。关键词是"整个团队"（whole team approach）和"共同负责"。

传统模式下测试是独立部门、独立阶段、独立 KPI。敏捷模式下——

| 维度 | 传统测试 | 敏捷测试 |
|---|---|---|
| 组织结构 | 独立 QA 部门 | 测试员编入 Scrum team |
| 介入时机 | 编码结束后 | 从需求 Kick-off 就介入 |
| 主要产出 | 测试用例文档 + 缺陷报告 | 自动化脚本 + 快速反馈 |
| 责任归属 | QA 部门为质量负责 | 全团队为质量负责 |
| 反馈周期 | 天 ~ 周 | 分钟 ~ 小时 |
| 用例生命 | 数月到数年 | 一到两个 Sprint |

"Whole team approach" 的实际含义是：开发也写测试、PO 也帮忙写验收标准、测试员也参与需求评审。质量不是 QA 一个岗位的事——是团队签了 Definition of Done 就得共同扛。

## 2. Lisa Crispin 的测试四象限

四象限是敏捷测试最有传播力的一张图。两个维度：

- 横轴：**面向业务**（Business-facing）vs **面向技术**（Technology-facing）
- 纵轴：**支持团队**（Supporting the team）vs **批判产品**（Critique the product）

分成四格：

| | 支持团队 | 批判产品 |
|---|---|---|
| 面向业务 | **Q2**：功能测试、故事测试、原型、模拟 | **Q3**：探索性测试、可用性测试、UAT |
| 面向技术 | **Q1**：单元测试、组件测试 | **Q4**：性能、安全、可靠性、"-ility" 测试 |

四象限不是流水线顺序——不是先 Q1 再 Q2 再 Q3 再 Q4。它是一种**覆盖检查**：一个健康的敏捷团队应该在四个象限都有活动，否则质量就是瘸的。

看每个象限具体做什么：

**Q1 — 支持团队的技术测试**。开发一边写代码一边写的东西：单元测试、组件测试、TDD 循环里的红-绿-重构。工具是 JUnit、pytest、Go test。这个象限的测试跑得快（毫秒级），跑得勤（每次 commit），是快速反馈的核心。相关内容在 [白盒测试](./动态测试：白盒测试.mdx) 里详谈。

**Q2 — 支持团队的业务测试**。围绕用户故事的功能测试：给定这个故事，怎么算做完了？验收标准（Acceptance Criteria）就是这里的产物。工具是 Cucumber、SpecFlow、Robot Framework。BDD、ATDD 都属于 Q2，下一节详细说。

**Q3 — 批判产品的业务测试**。人做的测试：[探索性测试](./探索性测试.mdx)、可用性测试、UAT、Alpha/Beta。这里靠的是人的判断力——软件"能跑"和"好用"是两回事，只有人能评估后者。

**Q4 — 批判产品的技术测试**。性能、压力、安全、渗透、可靠性、可安装性——所有 "-ility"。工具是 JMeter、Gatling、k6、ZAP、Burp Suite。这些细分在 [专项测试](./按目标：专项测试.mdx) 里展开。

一个 Sprint 里四个象限的分配不是均分。经验值：Q1 和 Q2 是每天都在做的，Q3 每个 Sprint 都要留出时间，Q4 可以按需在几个 Sprint 里做一次深度测试。

## 3. TDD、BDD、ATDD 有啥区别

这三个词经常被混着用，但侧重点不一样。

**TDD（Test-Driven Development）**：Kent Beck 提出，红-绿-重构循环。写测试 → 写最小代码让测试通过 → 重构。TDD 的输出是**代码级测试**，主要落在 Q1。

**ATDD（Acceptance Test-Driven Development）**：写代码之前，先和 PO 一起把验收测试写好。验收测试用业务语言写，跑起来就是自动化验收。落在 Q2。

**BDD（Behavior-Driven Development）**：Dan North 提出的 ATDD 演化版，强调"用统一的语言描述行为"。Given-When-Then 语法（Gherkin）就是 BDD 的标志。

一个 Gherkin 例子——测优惠券叠加：

```gherkin
Feature: 优惠券叠加规则

  Scenario: 金牌用户叠加两张品类券
    Given 用户 "cailey" 是金牌会员
    And 购物车里有 2 件 "运动" 品类商品
    And 用户持有满 100 减 10 的运动品类券
    And 用户持有满 200 减 30 的会员日券
    When 用户在结算页勾选叠加使用
    Then 订单总优惠应为 40 元
    And 订单实付金额应为 160 元
```

这段文本三个角色都能看懂：PO 用它描述需求、测试员用它写用例、开发用它跑测试（Cucumber 把 Given/When/Then 步骤映射到代码 step 定义）。三个视角同一份产物，这就是 BDD 的"沟通价值"，比自动化本身还重要。

三者的对比：

| 方法 | 谁写 | 落在哪个象限 | 目的 |
|---|---|---|---|
| TDD | 开发 | Q1 | 驱动代码设计 |
| ATDD | PO + 测试 + 开发 | Q2 | 定义"完成"的标准 |
| BDD | PO + 测试 + 开发 | Q2 | 用共同语言描述行为 |

## 4. Shift-Left 和 In-Sprint 测试

Shift-left（左移）字面意思是"把测试往开发流程的左边（早期）挪"。听起来像句废话，但实际含义具体：

- 需求评审时测试员在场，负责挑漏洞（"这个字段没说边界值")
- 设计评审时测试员在场，负责问可测性（"这个异步流程怎么等到执行完")
- 编码开始时验收测试已经写好，开发写代码是"让验收测试变绿"
- 单测跑绿之后才允许合并，CI 上跑组件测试和契约测试

一个 Sprint 里典型的时间线（Sprint 长度 10 个工作日）：

```
D1  D2  D3  D4  D5  D6  D7  D8  D9  D10
├── 需求细化、AC 写作、可测性评审
    ├── 开发 + 单测（TDD 循环）持续
        ├── ATDD 场景实现、契约测试
            ├── 自动化 API/UI 测试补齐
                ├── 探索性测试 session
                    ├── 回归自动化跑 + UAT
                        └ Sprint Review + Retro
```

关键点是：**没有"测试阶段"**。测试和开发是并行的，Sprint 最后一两天做的是回归和探索，不是"开始测试"。这就是 in-sprint 测试要达到的效果。

要做到 in-sprint，团队得先解决几个前置问题：

- CI/CD 得能自动跑测试并快速反馈（10 分钟以内是可接受，1 小时以上就废了）
- 测试环境得足够稳定（不能今天挂 database、明天挂 mock server）
- 测试数据得能程序化生成或按 fixture 复用
- Definition of Done 里得明确写"所有 AC 通过 + 单测覆盖 + 回归绿"

## 5. 敏捷测试的三个真实挑战

理论说完，看实践里坑最多的三个地方。

**挑战一：In-sprint 测不完怎么办**。Sprint 只有两周，需求量往往超过测试团队消化速度。常见的对策：

- 把测试自动化的开发时间计入 Sprint 容量（不能"外挂"）
- 允许"测试债"（Testing Debt）显式登记，下个 Sprint 优先偿还
- 引入 hardening sprint（每 3-4 个功能 sprint 插一个专门做 Q3/Q4 深测的 sprint），但这本质上是妥协
- 更激进的：改动 Definition of Done，把"通过全部 AC 自动化"作为合并门槛

**挑战二：自动化投入怎么摊销**。自动化脚本本身也是代码，也要维护，也要重构。一个反直觉的事实是：**自动化脚本越多，长期维护成本越高，除非你有很好的抽象层**。所以别追求"用例 100% 自动化"，而是分层：

| 层级 | 数量 | 稳定性要求 | 运行频率 |
|---|---|---|---|
| 单元测试 | 数千 ~ 数万 | 极高 | 每次 commit |
| 组件/契约测试 | 数百 ~ 数千 | 高 | 每次 PR |
| API 测试 | 数十 ~ 数百 | 中 | 每日 |
| E2E UI 测试 | 十几 ~ 几十 | 低 | 每次发布 |

这个金字塔叫 Test Pyramid，Mike Cohn 提出。倒过来的反模式叫 Ice Cream Cone——顶部 UI 测试特别多，底部单测很少——是敏捷测试里最常见的失败姿势。详情看 [自动化测试](./自动化测试.mdx)。

**挑战三：测试员在 Scrum team 里的角色定位**。传统 QA 岗位职责相对清晰：写用例、执行、报缺陷。放进 Scrum team 之后角色反而模糊：

- 是继续按用例数量结绩效？（不行，会激励写没用的用例）
- 是按发现的缺陷数？（不行，会激励和开发对抗）
- 是按 Sprint 里参与的 refinement 会议数？（更不行）

比较健康的答案是：测试员的定位从"执行者"变成"质量教练"——帮团队建立质量意识、设计可测的架构、维护自动化基础设施、做 Q3 探索。这也是 Lisa Crispin 强调的"generalizing specialist"（能一专多能的专才）。

## 6. 敏捷测试 ≠ 只做敏捷测试

一个常见误解：既然是敏捷，那就不写用例、不做 [静态测试](./静态测试技术.mdx)、不做 [变异测试](./变异测试.mdx)。恰恰相反——敏捷测试是把这些技术**编排进节奏**里，而不是砍掉。

- 静态测试：Code Review 是每 PR 都做的静态测试
- 白盒/黑盒：单元测试是白盒、Q2 的功能测试是黑盒，两者一起用
- 精准测试：可以用来决定 Sprint 内跑哪些回归、跳哪些
- 变异/模糊：Q4 的一部分，属于深度测试

敏捷测试的本质是**流程重排**，不是**技术减法**。

## 7. 局限

四象限图很好用，但也别把它当圣经。它是 2009 年画的，云原生、AI 系统、大模型这些新形态在图里没有对应位置——比如"如何测试一个 RAG 系统的 hallucination"就跨了 Q2 和 Q3 还带一点 Q4。

Whole team approach 在成熟的团队很香，在新组的团队常常翻车——开发不写单测、测试员被当成资源池、PO 不写 AC——最后回退到"迷你瀑布"。这时候敏捷测试就是名义上的。

Sprint 节奏和监管场景冲突。医疗、汽车、航空需要保留完整的测试证据链、遵循 IEC 62304、ISO 26262，敏捷的"用例即代码"很难满足。这些行业里敏捷测试常常是"敏捷开发 + 瀑布验证"的混合体。

自动化优先在 UI 高频变化的产品里成本极高。前端两周改一版 UI，UI 自动化脚本永远在修。这时候更理性的选择是砍 UI 自动化、加强 [探索性测试](./探索性测试.mdx) + API 层自动化。

## 8. 敏捷测试在测试家谱里的位置

往前看，敏捷测试继承了 XP（极限编程）的 TDD 和 Whole team、Scrum 的迭代节奏、Lean 的浪费识别。往后看：

- [探索性测试](./探索性测试.mdx)：Q3 象限的主力，几乎是敏捷测试的双胞胎
- [自动化测试](./自动化测试.mdx)：Q1/Q2 的实现手段，测试金字塔的载体
- [混沌工程与弹性测试](./混沌工程与弹性测试.mdx)：Q4 象限在云原生下的极致演化
- [精准测试](./精准测试.mdx)：解决"敏捷回归怎么跑得完"的现代答卷
- [测试过程与生命周期](./测试过程与生命周期.mdx)：整体框架，敏捷是其中一种形态
- DevOps 测试、Continuous Testing：把敏捷测试的"in-sprint"进一步推到"in-pipeline"

敏捷测试不是终点，它是从瀑布测试到持续测试的过渡态。理解了它的四象限和 Whole team 精神，其他现代测试方法基本都能在这张图上找到自己的位置。
