## 钱包与密钥安全

区块链圈子里有句常挂在嘴边的话:"Not your keys, not your coins。"意思是,如果你把币放在交易所,那些币其实并不真正属于你,因为你手上没有钥匙。反过来说,一旦你自己保管私钥,资产的最终归属就取决于这把钥匙掌握在谁手里。这一节我们从密码学的底层聊到工程实践,试图把"钱包安全"这件事讲透。

### 一切从椭圆曲线开始

比特币和以太坊都用了同一条椭圆曲线,叫 secp256k1。我们不深入代数,只需要把它想象成一个巨大的循环群,曲线上的点可以相加,也可以做整数倍——就像时钟的分针一样在一个封闭的世界里绕圈。这个群有一个约定俗成的基点 $G$。

私钥就是一个 256 位的整数 $d$,原则上是均匀随机的。公钥是曲线上的一个点,由私钥和基点相乘得到:

$$Q = d \cdot G$$

这里的乘法是曲线上的"点乘"。它有个非常特别的性质:算 $Q = d \cdot G$ 是容易的,但反过来,从 $Q$ 和 $G$ 求出 $d$ 属于椭圆曲线离散对数问题,目前没有已知的高效算法——用现有算力,穷举 256 位空间是几十亿年起步。这个"单向"就是所有链上安全的地基。

有了公钥,我们再往前走一步得到地址。以太坊的地址是公钥做一次 Keccak-256,取后 20 字节;比特币的地址是公钥做 SHA-256,再做一次 RIPEMD-160,最后 Base58Check 编码。为什么要多做一次哈希?一是让地址短一些好显示,二是多加一层保护——真到量子计算机能破 secp256k1 的那天,只要地址没花过钱,公钥就还没暴露,资金还能撑一会儿。

### 签名与验签

有了私钥,我们就可以签名了。ECDSA 的公式看起来有点吓人,我们把它拆开看:

第一步,随机取一个数 $k$;
第二步,计算曲线点 $R = k \cdot G$,取 $R$ 的横坐标为 $r$;
第三步,计算 $s = k^{-1}(h + rd) \bmod n$,这里 $h$ 是消息的哈希,$d$ 是私钥。

最终的签名就是二元组 $(r, s)$。验证的一方只需要公钥、消息哈希和签名,就可以验证签名的有效性,却无法反推出私钥。

大部分时候我们不需要自己实现 ECDSA,库都写好了。但有一个坑我们必须知道,因为它历史上导致过几次大事故。

### 一个致命的坑:k 值重用

回到签名公式:$s = k^{-1}(h + rd) \bmod n$。如果同一个私钥,在两次不同的消息上用了**同一个** $k$,会发生什么?

设两次签名分别是 $(r, s_1)$ 和 $(r, s_2)$,对应消息哈希为 $h_1$、$h_2$。因为 $k$ 一样,所以 $r$ 也一样。把两个方程联立消掉 $k$:

$$k = \frac{h_1 - h_2}{s_1 - s_2} \bmod n$$

$k$ 一出来,私钥 $d$ 立刻可以反推出来。也就是说,**两次 k 相同的签名,等于把私钥挂在了公告板上**。

历史上这个坑掉过几次:2010 年索尼 PS3 的私钥被 fail0verflow 破解,靠的就是 k 重用;2013 年 Android 的 `SecureRandom` 有 bug,导致部分比特币钱包实际用了固定的 k,一批地址被自动脚本清空。

现代的做法叫 RFC 6979:直接把 $k$ 定义为 $\text{HMAC}(d, h)$,确定性生成、完全不依赖随机数生成器。以太坊的 ethers.js、Bitcoin Core、libsecp256k1 都已经这么做了。这也提醒我们一个更普遍的教训:任何"应当是均匀随机"的地方,如果依赖底层 RNG,都是潜在的雷区,能确定性化就确定性化。

### 助记词与 HD 钱包

如果每一个地址都要单独备份一份 256 位私钥,用户体验就爆炸了——想想让爷爷奶奶手抄 64 个十六进制字符还得一位不错。业界的解决方案叫分层确定性钱包,由三个 BIP 提案定义:

BIP-39 把 128 到 256 位的随机熵编码成 12 到 24 个英文单词——这就是我们熟悉的"助记词"。它比十六进制好抄、好念、好检查。

BIP-32 定义了从一个种子出发,通过 HMAC-SHA512 派生出任意层级子密钥的算法。它让"一份种子对应无数个地址"成为可能。

BIP-44 则约定了标准的派生路径 `m / purpose' / coin_type' / account' / change / index`。以太坊的标准路径是 `m/44'/60'/0'/0/0`,比特币是 `m/44'/0'/0'/0/0`。这是不同钱包之间能互相识别对方账户的基础。

完整流程可以这样理解:

```
助记词 → PBKDF2(2048 轮 + 可选 passphrase) → 512 位种子
种子 → BIP-32 派生 → 主密钥 → 按路径派生 → 子私钥
子私钥 → secp256k1 → 公钥 → Keccak → 地址
```

有几个安全上的含义值得反复强调。第一,助记词等于所有账户的主钥。抄错一个词或者拍照传云盘,全部资产就有暴露风险。第二,BIP-39 允许在助记词之外再加一个 passphrase,俗称"第 25 个词"。这个词不进助记词本身,可以形成一个"隐藏钱包",但代价是丢了 passphrase,助记词也救不了你。第三,BIP-32 有一个不太出名的坑:非硬化派生(路径里不带撇号 `'`)下,只要有子公钥加 chain code,就能推出所有子公钥的公钥;此时如果**任意一个**子私钥再被泄漏,可以反推父私钥。所以硬件钱包默认对账户层做硬化派生。

### 钱包类型与它们的威胁模型

不同的钱包对应不同的用户场景和威胁模型。我们把常见的几种放在一起比较。

热钱包是浏览器插件或 App,像 MetaMask 和 Rabby。私钥加密后存在本地,联网。它们方便日常操作,但直接暴露在恶意扩展、钓鱼网站、剪贴板劫持等威胁面前。适合放小额、日常交互。

硬件钱包比如 Ledger、Trezor。私钥存在专用安全芯片里,永远不出设备;签名时消息通过 USB 送进去,签名结果送出来。它们把"私钥离开设备"的攻击面砍掉了,但换来了三个新的攻击面:供应链攻击(非官方渠道买的设备可能被改)、盲签(设备屏幕太小,复杂交易看不清)、以及物理胁迫(有人拿枪指着你的时候,硬件钱包也没用)。适合中大额长期持有。

多签钱包比如 Safe。要求 N 把钥匙里签够 M 把才能出账。它把"一把钥匙一次泄漏就完蛋"变成了"多个签名人同时被攻破才完蛋"。适合团队金库和 DAO 金库。

MPC/门限签名走得更远,私钥从来不作为一个完整的对象出现在世界上任何地方——各方持有分片,签名时通过一个多方计算协议合作生成完整签名。适合交易所、大额托管。

智能合约钱包(账户抽象)则把钱包本身写成合约,支持用邮箱、Passkey、多签、社交恢复等一系列传统私钥模型做不到的功能。代价是合约本身可能有 bug,而 bug 直接对应资金损失。

### 几种常见的攻击

再从"钱是怎么丢的"这个角度过一遍。

第一类是**钓鱼签名**。近两年最泛滥的手法。用户被诱导签一个看似无害的消息,其实是 EIP-712 结构化数据授权,比如 Permit 允许某个地址无限花你的稳定币。签下去之后攻击者拿这个签名去合约里花你的钱。这里最关键的点是:签名和交易不一样,签名不会立刻上链,不花你的 gas,但可以被别人拿去 relay 上链。也就是说,签名可以在你没有反应过来的时候变成一笔转账。防御方法只有一条——签之前认真读签名内容,尤其是 `verifyingContract` 和 `spender` 字段,不熟的域名拒签。

第二类是**无限授权**。DEX、桥、聚合器上一次 `approve(spender, uint256.max)` 就再也不用弹窗,这是个用户体验优化,但代价是 spender 合约一旦出漏洞或者被换成恶意版本,那种代币在你钱包里就全部可被抽走。建议定期用 Revoke.cash 清理陈旧授权;或者更好的是用 EIP-2612 的 `permit`,每次一次性授权,而不是一劳永逸地把大门敞开。

第三类是**地址投毒**。攻击者用碰撞工具生成一个前后几位都和你常用地址相同的地址,然后向你转 0 USDT,让这个地址进入你的交易历史。下次你从历史里复制地址粘贴时,眼睛没看仔细,就转到了攻击者手里。这类攻击提醒我们一个非常简单的习惯:永远校验完整地址,或者用 ENS 之类的可读名字代替裸地址。

第四类是**弱随机私钥**。有人图省事用 `Math.random()` 或系统时间做种子生成私钥,搜索空间小到几分钟就能被自动脚本扫完。历史上有专门的东西叫 "Ethercombing":扫描所有基于弱熵生成的地址,秒扫其中的余额。结论就是,私钥必须来自密码学级别的随机源,`/dev/urandom`、`crypto.getRandomValues`、硬件 TRNG,永远不要自己实现随机。

第五类是**靓号地址**。2022 年发现,用 Profanity 生成的漂亮地址(比如全 0 开头)因为熵源缺陷可以被反推。Wintermute 因此损失了 1.6 亿美元。这里的教训是:让地址看起来好看,是有代价的。

### 硬件钱包并不是万能

不少人以为买了硬件钱包就一劳永逸,这是个非常危险的错觉。硬件钱包解决的只是"私钥不离设备"这件事,它并不能替你判断"你正在签的这笔交易到底是什么"。

具体来说,盲签的问题很棘手。硬件钱包屏幕小,一笔复杂的 DeFi 交易可能有几十字节的 calldata,设备根本没法完整展示。用户看到的往往只是一串十六进制,只能凭信任按下确认键。Ledger 后来推出的 "Clear Signing" 就是在解决这个——让常用协议的合约把交易含义翻译成人话展示到设备上。但覆盖率仍然远不完全。

供应链攻击也是个真实威胁。从二手平台或非官方渠道买来的硬件钱包可能已经被预置了助记词——你以为是新设备,实际上你导入的每一笔资金都会被搬空。永远从官网订购,永远自己重新生成助记词。

至于物理胁迫,这是所有安全方案的共同弱点。有人拿枪指着你的时候,再强的密码学也没意义。这类场景的现实防御方案是"诱饵钱包":用 BIP-39 passphrase 做出一个明面上的小额钱包,真正的资产藏在另一个 passphrase 下——被胁迫时把诱饵交出去。

### 账户抽象

传统钱包模型有一个根本约束:每笔交易必须由 EOA(外部账户)签名,而 EOA 的签名算法只能是 secp256k1 ECDSA。这个限制让钱包很难做出用户友好的功能。

EIP-4337 提出的账户抽象打破了这个限制:让钱包本身也是一个智能合约。合约里可以自定义任意"验证逻辑"——用 Passkey 签?可以;要求两把私钥同时签?可以;每天限额多少?可以;可疑操作触发人工确认?也可以。用户不再需要拿一段十几字节的助记词换取所有权,可以用生物识别、社交恢复等更贴近日常的方式管理资产。

代价是,合约本身成了新的攻击面:实现有 bug 就是资金损失;Bundler、Paymaster 之间的信任关系也需要设计好。ERC-7579 和 ERC-6900 都在标准化这套模块化钱包架构,让不同钱包厂商的组件可以互操作。

账户抽象是未来的方向,但它不是"更安全",而是"把复杂度从人身上转移到了代码上"。代码里的复杂度会不会自己爆掉,还得看行业积累。

### 备份的现实操作

理论讲了不少,最后我们落到一个非常具体的问题:助记词到底怎么存?

一份可以直接照着做的建议是这样的:

第一,不要把助记词整份放在同一个地方。用 Shamir Secret Sharing 分成 3-of-5 份,或者简单地拆成两部分,放在几个物理位置——家里保险柜、亲戚家、银行保险箱。任何一份丢失都不至于损失全部,任何一份被偷也拿不到完整助记词。

第二,不要用纸。纸怕火、怕水、怕虫。可以用金属助记词板,几十块钱一块,能扛得住多数常见灾难。

第三,加一个 BIP-39 passphrase,和助记词分开存放。这样即使助记词整份被拿到,没有 passphrase 也用不了。但注意 passphrase 忘了就永远找不回,一定要自己能记得住或者有可靠的备份方式。

第四,大额资产上多签。一个人一部手机的方案在小额下可以接受,但几百万美元的资金放在单私钥上是巨大的单点风险。Safe 的 3-of-5 多签是行业实践。

第五,定期做恢复演练。在一台干净的新设备上试着恢复钱包,确认助记词、passphrase、派生路径都能正确对应回你的地址。这一步很多人从来没做过,直到某一天设备丢了才发现备份有问题。

### 小结

钱包的核心是一把私钥,私钥的核心是随机性和一次性使用。密码学层面的 ECDSA、BIP-32/39/44 已经很成熟,但真正让人丢钱的往往不是密码学,而是工程实践和使用习惯——签名时没看清、授权时给了无限、备份时放在了错的位置、买设备时选了错的渠道。

安全不是一次搞定的事,而是长期的习惯。这一节的每一条建议都不复杂,但只有当我们真的把它变成肌肉记忆,才能在攻击者永不休息的世界里活下去。

### 练习

1. 阅读一份 ECDSA 库的源码(比如 Python 的 `ecdsa` 或 JavaScript 的 `elliptic`),找出它是怎么生成 $k$ 的。它用了 RFC 6979 吗?
2. 用 Python 从零实现一遍 BIP-39:随机 128 位熵 → 计算校验位 → 查词表得到 12 个词 → PBKDF2 得到种子。然后再自己实现从种子派生第一个以太坊地址(BIP-32 + BIP-44)。这个练习会让你对助记词到地址的完整路径产生非常清晰的图像。
3. 找一个你在 MetaMask 里签过的 EIP-712 消息,把 JSON 拆开看每个字段的含义。想想如果这个签名是恶意的,你能不能通过看 JSON 提前发现问题。
4. 假设你有 100 万美元加密资产,要设计一个存储方案让"任何单点失败都不至于损失全部,任何三点同时失败也不至于损失全部"。你会怎么做?这不是理论题,行业里的机构真的这么设计。
