# 按目标：专项测试——功能之外的九个维度

如果 [按粒度：测试层次](./按粒度：测试层次.mdx) 回答的是"测多细"，那这篇回答的是"测哪个维度"。功能测试只是测试的**默认维度**——功能对了，软件不一定能用。速度慢一秒、被 SQL 注入、盲人打不开、字符编码乱掉，任何一条都能让功能正常的软件毁掉。专项测试就是把这些"功能之外的维度"一个个拎出来单独打。

## 1. 为什么要有专项测试

先看一个真实场景。某电商大促前压力测试没做，功能测试全通过，上线首日凌晨 12 点开抢——服务器 CPU 直接打满，接口 p99 从 200ms 涨到 30 秒，用户点下单转圈 5 分钟后订单重复提交 3 次，风控误判为刷单封了一批 VIP 账号，客服工单第二天爆掉。

这个事故里没有一个"功能 bug"。下单接口逻辑对、库存扣减对、支付回调对。挂的是**性能**、**并发下的一致性**、**风控在异常流量下的鲁棒性**——三个功能测试不覆盖的维度。

专项测试的意义就是把这些非功能维度显性化。ISO/IEC 25010 软件质量模型把非功能属性分成八个大类，工业界常谈的是下面这七个专项。

## 2. 性能测试

**关心什么**：单个请求的响应时间、系统的吞吐量、资源占用（CPU、内存、IO）。

**典型指标**：

| 指标 | 含义 | 常见目标 |
|---|---|---|
| 响应时间 p50/p95/p99 | 一半/95%/99% 的请求耗时低于此值 | Web 接口 p99 < 500ms |
| QPS/TPS | 每秒查询/事务数 | 视业务而定 |
| 并发用户数 | 同时在线的用户数 | 电商大促 100 万+ |
| 资源占用 | CPU / 内存 / 网络 / 磁盘 IO | CPU < 70%，留 buffer |

看 p99 不看平均，是因为**平均值掩盖长尾**。1000 个请求，999 个 100ms、1 个 10 秒，平均 110ms 看着很好，实际那 1 个 10 秒是活生生的一个愤怒用户。

**工具**：JMeter（老牌 GUI）、k6（脚本化、云原生首选）、Locust（Python 编写用例）、wrk（轻量级 HTTP 压测）、Gatling（Scala 写用例，报告漂亮）。

**什么时候做**：功能稳定后、上线前一次全量压测；每个大版本迭代都要跑基准回归；重要促销/活动前专项加码。

## 3. 压力测试 / 负载测试 / 容量测试

这几个词经常混用，实际是不同问题：

| 测试类型 | 目的 | 做法 |
|---|---|---|
| 负载测试 | 在预期负载下能否达到 SLA | 按预期 QPS 打 30 分钟 |
| 压力测试 | 系统的极限在哪里、如何崩溃 | QPS 逐步加压直到崩溃 |
| 容量测试 | 达到目标 QPS 需要多少资源 | 固定 QPS，看资源占用 |
| 稳定性测试 | 长时间跑会不会内存泄漏 | 中等负载连续跑 24–72 小时 |
| 尖峰测试 | 流量瞬时暴涨能否扛住 | QPS 秒级从 1x 拉到 10x |

**压力测试的价值不是找到极限数字**，而是找到**崩溃模式**：数据库连接池先耗尽还是内存先炸？服务先 OOM 还是 GC 先卡住？知道崩溃模式才能设计降级和限流。

**稳定性测试的重要性容易被低估**。JVM 应用的内存泄漏、连接不释放这类问题，短时压测根本发现不了，必须跑够长时间。

## 4. 安全测试

**关心什么**：系统能不能防住恶意输入、越权访问、数据泄露、拒绝服务。

安全测试有一套标准分类——OWASP Top 10 每年更新，是 Web 应用最常见的十种漏洞：注入、认证失效、数据泄露、XXE、访问控制失效、安全配置错误、XSS、反序列化、组件漏洞、日志不足。

| 子类型 | 干什么 | 工具 |
|---|---|---|
| SAST | 静态代码扫描漏洞 | SonarQube、Semgrep、Checkmarx |
| DAST | 动态扫描运行中的应用 | OWASP ZAP、Burp Suite |
| SCA | 扫描第三方依赖漏洞 | Snyk、Dependabot、Trivy |
| 渗透测试 | 人工模拟攻击 | 通常外包给专业团队 |
| Fuzz | 随机输入找崩溃/漏洞 | 见 [模糊测试](./模糊测试.mdx) |

**渗透测试和自动化扫描不能互相替代**。自动化扫描能覆盖已知漏洞模式，但业务逻辑漏洞（比如"改一下订单 ID 就能看别人的订单"）机器识别不出来。渗透测试贵但必要。

一个我见过的经典业务逻辑漏洞：某 App 的优惠券领取接口没做用户校验，但客户端做了。用 Charles 抓包改一下用户 ID，可以给任何人的账号发满 100 减 50 的券。功能测试永远发现不了，因为客户端行为完全正常。

## 5. 可用性测试（Usability）

**关心什么**：用户能不能顺畅地完成任务、界面是否符合直觉、错误信息是否有帮助。

注意区分两个词：**可用性（usability）** 是"好不好用"，**可用性（availability）** 是"能不能用（系统在不在线）"，中文都叫可用性但完全不是一个东西。工业界谈 SLA 5 个 9 是后者，谈 UX 是前者。

可用性测试的核心方法：

- **用户走查（Cognitive Walkthrough）**：让真实用户完成典型任务，观察他们卡在哪
- **启发式评估（Heuristic Evaluation）**：专家按 Nielsen 十大原则打分
- **A/B 测试**：两版界面各投放一部分用户，看指标（点击率、转化率、完成时间）

指标偏定性：任务完成率、任务完成时间、错误率、满意度评分（SUS 量表 0–100 分，70+ 算好）。

工具偏软：UserTesting、Hotjar（热力图和录屏）、Maze（原型可用性测试）。

可用性测试和 [探索性测试](./探索性测试.mdx) 有重叠但目的不同——探索性关心"有没有 bug"，可用性关心"用户会不会用"。

## 6. 兼容性测试

**关心什么**：软件在不同环境下是否表现一致。

维度非常多：

| 维度 | 例子 |
|---|---|
| 浏览器 | Chrome / Firefox / Safari / Edge / 国产内核 |
| 操作系统 | Windows 10/11、macOS、各版本 Linux、Android/iOS 版本 |
| 设备 | PC、手机、平板、Ultra-wide 显示器、折叠屏 |
| 屏幕分辨率 | 4K、1080p、720p、异形屏 |
| 网络 | 4G / 5G / WiFi / 弱网 |
| 数据库 | MySQL 5.7 / 8.0、PostgreSQL 各版本、Oracle |
| 输入法 | 中文、日文、韩文、emoji |

兼容性组合爆炸——3 个 OS × 4 个浏览器 × 3 个屏幕分辨率就是 36 种组合。**必须做优先级排序**：按用户数据挑最主流的 5–10 个组合覆盖，长尾靠 crash 上报兜底。

**工具**：

- BrowserStack、Sauce Labs——云端多浏览器多设备真机测试
- Selenium Grid / Playwright——本地并行多浏览器
- WebPageTest——测各种网络条件下的表现

## 7. 可访问性测试（Accessibility, a11y）

**关心什么**：残障用户能不能用你的软件。

a11y 是 "accessibility" 中间省略 11 个字母。核心标准是 WCAG 2.1，分 A / AA / AAA 三个级别。政府网站、金融应用、教育平台通常法规要求 AA。

四个核心原则（POUR）：

| 原则 | 含义 | 检查点举例 |
|---|---|---|
| 可感知（Perceivable） | 用户能感知到内容 | 图片有 alt、视频有字幕 |
| 可操作（Operable） | 用户能操作界面 | 键盘能到达所有功能 |
| 可理解（Understandable） | 内容和操作可理解 | 表单错误信息明确 |
| 稳健（Robust） | 兼容辅助技术 | 屏幕阅读器能读出 |

**工具**：axe DevTools（Chrome 扩展）、Lighthouse（Chrome 内置）、WAVE、Pa11y（可自动化）。

自动化只能覆盖 30–40% 的可访问性问题。剩下的必须手动测——闭上眼睛用屏幕阅读器过一遍你的应用，是所有前端工程师都应该做一次的事。做完你会明白很多"看着挺好"的设计对盲人是灾难。

## 8. 国际化 / 本地化测试

**关心什么**：软件能不能在不同语言和地区下正常工作。

区分两个词：**国际化（i18n）** 是"技术上能不能支持多语言"，**本地化（l10n）** 是"针对某个地区的具体适配"。i18n 是基础设施，l10n 是内容。

i18n 测试典型问题：

- 字符编码：中文、日文、emoji、俄语能不能正确显示、存储、搜索
- 文本膨胀：德语单词长、日语短，UI 排版会不会溢出
- 从右到左：阿拉伯语、希伯来语，整个布局要镜像
- 日期/数字格式：`2026-08-25` vs `25/08/2026` vs `8/25/2026`
- 时区：所有时间存 UTC 显示时转本地，坑无数
- 货币：CNY、USD、JPY 的小数位数、千分位符号
- 排序：不同语言的字典序不同（德语 Ö 该排在 O 还是 Oe？）
- 表单验证：邮编、电话、身份证格式因国家不同

**l10n 测试**关注翻译质量、文化适配（图标含义、颜色象征）、法律合规（GDPR、CCPA）。

## 9. 其他常见专项

不展开，简单列一下：

| 专项 | 关心什么 |
|---|---|
| 安装/升级测试 | 安装能否成功、升级能否保留数据、回滚是否可行 |
| 灾难恢复测试 | 主数据中心挂了备中心能否接管、RTO/RPO 达标 |
| 数据迁移测试 | 老库迁新库数据不丢、schema 变更前后一致 |
| 备份恢复测试 | 备份能不能真的恢复出可用数据 |
| 合规测试 | 满足 GDPR、HIPAA、PCI-DSS 等法规要求 |
| 弹性测试 | 见 [混沌工程与弹性测试](./混沌工程与弹性测试.mdx) |
| 环境测试 | 温度、湿度、电磁干扰下的表现（嵌入式/硬件） |

## 10. 什么时候做什么专项

不是所有专项都每个版本都要做。粗略的排期建议：

| 阶段 | 强制专项 | 推荐 | 视情况 |
|---|---|---|---|
| 每次 PR / CI | 单元、集成、静态安全扫描 |  |  |
| 每次发版 | 冒烟、回归、SCA 依赖扫描 | a11y、性能基准 |  |
| 大版本 | 上述 + 完整性能压测 | 兼容性、安全渗透 | i18n |
| 促销/活动前 | 压力、尖峰、稳定性 | 灾难恢复演练 |  |
| 年度 | 完整渗透测试 | 灾备切换演练 | 合规审计 |

真实项目的时间和预算总是有限，专项测试的核心是**风险优先**。金融应用把安全放第一，游戏把性能放第一，政府应用把可访问性放第一，SaaS 把兼容性放第一。

## 11. 局限

专项测试有几个通病：

**指标游戏化**：p99 < 500ms 是目标，但真出问题的是 p999 或 p9999——那些偶发的、被平均掉的极端 case。追指标追到指标好看了，用户体验没提升。关于度量陷阱的更多讨论见 [测试管理](./测试管理.mdx)。

**环境失真**：性能测试在测试环境跑得飞起，上线扑街——因为测试环境的数据规模、并发模式、依赖抖动都跟生产不一样。真正准的性能数据必须在生产或接近生产的环境测，这也是 shift-right 和影子流量的动机之一。

**专项之间的耦合被忽略**：安全策略拖慢性能、i18n 增加内存、a11y 影响加载速度。单独优化每个专项，加起来可能整体变差。

**专项独立于层次**：一个性能问题可以在单元（一个函数的 benchmark）、集成（一个服务的 QPS）、E2E（整条链路的 p99）三个层次上测，同一个"性能测试"名词在不同层次含义差很多。看到"我们做了性能测试"要追问是哪一层。

专项测试是**目标维度**，跟其他维度组合起来才是完整策略：

- 时机维度：[测试过程与生命周期](./测试过程与生命周期.mdx)——每个专项都要选阶段
- 方法维度：[静态测试技术](./静态测试技术.mdx)、[动态测试：白盒测试](./动态测试：白盒测试.mdx)、[动态测试：黑盒测试](./动态测试：黑盒测试.mdx)
- 深入的专项方法：[模糊测试](./模糊测试.mdx)（安全）、[混沌工程与弹性测试](./混沌工程与弹性测试.mdx)（弹性）
- 工程支撑：[自动化测试](./自动化测试.mdx)、[测试工具简介](./测试工具简介.mdx)、[测试管理](./测试管理.mdx)

功能测试是及格线，专项测试是差异化的地方。用户不会因为你的功能对了给你 5 星，但会因为你 3 秒打不开、盲人不能用、大促崩了给你 1 星。
