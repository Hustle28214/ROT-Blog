# 按粒度：测试层次——从单元到端到端

测试的第一个划分维度是**粒度**：你到底在测多大一块东西？一行函数、一个模块、一个服务、还是一整条用户链路？不同粒度回答不同问题、用不同工具、承担不同成本。这篇讲这五个层次之间的关系，以及为什么"金字塔"这个形状会成为工业界的默认答案。

## 1. 五个层次的定义

先把话说清楚。行业里的术语常混用，这里给一个我用起来最省事的定义：

| 层次 | 测什么 | 边界 | 依赖 |
|---|---|---|---|
| 单元测试 | 一个函数/类/方法 | 单文件、单进程 | 全部 mock |
| 集成测试 | 多个模块协作 | 一个服务内部 | 部分真实、部分 mock |
| 系统测试 | 整个系统 | 一个部署实例 | 全部真实 |
| 验收测试 | 用户价值 | 从用户视角 | 全部真实 |
| E2E 测试 | 端到端链路 | 跨服务、跨系统 | 全部真实 |

系统测试和 E2E 常被混着说。粗略的区分是：**系统测试**关心"这个系统本身能不能工作"，**E2E** 关心"这个系统在整条业务链路里能不能工作"。举例：一个订单系统，系统测试测"下单接口返回是否正确"，E2E 测"用户从选商品到付款到收到确认邮件是否走通"。

## 2. 用登录功能穿一遍

抽象定义容易糊。用一个具体功能——用户登录——过一遍每个层次到底怎么测。

**单元测试**：测密码校验函数。

```python
def test_verify_password_correct():
    hashed = hash_password("hunter2")
    assert verify_password("hunter2", hashed) is True

def test_verify_password_wrong():
    hashed = hash_password("hunter2")
    assert verify_password("wrong", hashed) is False

def test_verify_password_empty():
    with pytest.raises(ValueError):
        verify_password("", "any_hash")
```

只测函数本身。没有数据库、没有 HTTP、没有 Redis。跑一次几毫秒。

**集成测试**：测 AuthService 和数据库、缓存之间的协作。

```python
def test_login_updates_last_login_time():
    user = create_test_user("alice", "hunter2")
    result = auth_service.login("alice", "hunter2")
    assert result.success
    reloaded = user_repo.find_by_id(user.id)
    assert reloaded.last_login_at is not None

def test_login_rate_limit():
    for _ in range(5):
        auth_service.login("alice", "wrong")
    result = auth_service.login("alice", "hunter2")
    assert result.error == "rate_limited"
```

这里数据库和 Redis 都是真的（testcontainer 拉起来的），但没起 HTTP 服务。跑一次几秒。

**系统测试**：起完整的登录服务，通过 HTTP 接口测。

```
POST /api/login
Content-Type: application/json
{"username": "alice", "password": "hunter2"}

Expected: 200 OK
Body: {"token": "<jwt>", "expires_in": 3600}
```

用 Postman、Rest Assured 或者代码直接发请求。测的是接口契约、认证头、错误码、响应结构。跑一次几十秒。

**验收测试**：用产品经理写的验收标准。

```
Given 一个已注册的用户 alice
When alice 用正确密码登录
Then 页面跳转到首页
And 首页右上角显示 "欢迎，alice"
```

用 Cucumber、Behave 这类 BDD 工具，或者干脆用 Selenium 脚本。视角是"用户能不能完成他想做的事"，不再关心 JWT 结构。

**E2E 测试**：从浏览器开始，一路走到订单页。

```
1. 打开 https://example.com
2. 点击"登录"
3. 输入用户名密码
4. 点击"提交"
5. 等待跳转到首页
6. 点击"我的订单"
7. 验证订单列表能加载
```

用 Cypress、Playwright、Selenium。这里测的是登录后能不能把用户带进正常的业务流程——包含 CDN、网关、认证服务、订单服务、前端渲染的整条链路。跑一次几分钟。

同一个"登录"，五种测法测的是五个不同的问题。这是分层的意义。

## 3. 测试金字塔

Mike Cohn 在 2009 年提出的图，此后成了默认心智模型：

```
        /\
       /E2\        <- 少（几十条）
      /----\
     /  UI  \      <- 中（几百条）
    /--------\
   / 集成/API \    <- 多（几千条）
  /------------\
 /    单元测试   \  <- 巨多（几万条）
/________________\
```

金字塔的核心论断是：**下层要多、上层要少**。为什么？

|  | 单元 | 集成 | E2E |
|---|---|---|---|
| 单次运行速度 | 毫秒 | 秒 | 分钟 |
| 稳定性 | 高 | 中 | 低（flaky） |
| 反馈精度 | 定位到函数 | 定位到模块 | 只知道"挂了" |
| 编写成本 | 低 | 中 | 高 |
| 维护成本 | 低 | 中 | 极高 |

E2E 用例经常"挂但不知道为什么挂"——可能是被测服务挂了、可能是测试环境的网络抖动、可能是前端一个 class name 改了导致选择器失效。CI 里跑 200 个 E2E，稳定挂 5–10 个的场景太常见。这就是 flaky test 问题。

单元测试相反：函数改了、断言失败，一秒定位到具体哪个 case 挂了。修一次维护成本几乎为零。

所以金字塔的形状不是审美，是**成本-价值权衡的自然产物**。

## 4. 测试奖杯：前端时代的修正

金字塔在前端和一部分微服务场景下被质疑。Kent C. Dodds 在 2018 年提出"测试奖杯"（Testing Trophy）：

```
       ___________
      /           \
     /   E2E       \
    /_______________\
   /                 \
  /   Integration    \    <- 最粗那一层
 /_____________________\
 /                       \
 |        Unit           |
 |_______________________|
        _______
       |静态检查|          <- 底座
       |_______|
```

奖杯的形状是"集成最粗、单元变窄、增加静态检查底座"。为什么这么改？

- **前端组件难以做纯粹的单元测试**：React 组件、Vue 组件本身就是"输入 props、输出 DOM"的东西，脱离 DOM 环境的单测意义不大。把它们放进"渲染 + 交互"的集成测试里更划算。
- **静态检查提前拦截很多单元测试要测的问题**：TypeScript 让"传错参数类型"这类问题在编译期就被拦，不需要单测覆盖。
- **微服务里模块交互 bug 比单模块内部 bug 更多**：分布式系统的问题往往在边界上，集成测试的性价比就上去了。

金字塔和奖杯不是对立的，是**对不同场景的适应**。后端逻辑密集的服务用金字塔，前端组件密集的应用用奖杯，微服务架构介于两者之间。

## 5. 反模式：冰淇淋蛋筒

跟金字塔完全相反的形状——上宽下窄，Alister Scott 起的名字叫 "Ice Cream Cone"：

```
 \                  /
  \  巨多 E2E      /
   \______________/
    \            /
     \  一些 API /
      \________/
       \      /
        \单测/  <- 几乎没有
         \__/
```

出现这种形状的团队通常是这样的：开发不写单测（"太麻烦"、"覆盖率高又怎样"），QA 补大量 E2E 用例（"看得见摸得着"），结果每次发版跑 8 小时 E2E，flaky 一堆，改一行代码不知道会不会挂 20 个用例。

冰淇淋蛋筒不是不能工作，只是**运行成本极高、反馈极慢、回归极痛苦**。识别标志：CI 跑一次需要 30 分钟以上、E2E 挂了没人认真查、"重跑一次就好了"成了日常口头禅。

## 6. 每一层的测试重点差异

同一个功能在不同层次上，测试重点也不一样。以"下单"为例：

| 层次 | 重点 | 举例 |
|---|---|---|
| 单元 | 逻辑正确性 | 折扣计算函数在边界值上是否精确 |
| 集成 | 依赖协作 | 库存服务超时时订单服务能不能优雅降级 |
| 系统 | 接口契约 | POST /orders 在缺字段时返回 400 |
| 验收 | 用户价值 | 用户点"下单"能否在 3 秒内看到成功页 |
| E2E | 链路可达 | 下单后 30 秒内是否发出确认邮件 |

一个常见错误是**在错误的层次测错误的问题**。比如：

- 在 E2E 里测折扣计算的精度——用例极多、跑得慢、有一个挂了完全定位不到问题。这些应该在单元测。
- 在单元测试里 mock 掉数据库然后测"数据能不能正确落库"——mock 让测试变成"我 mock 了什么就返回什么"，根本没测到真正的东西。这些应该在集成测。
- 在系统测试里手工点 UI 验证功能——用完就丢，回归时又要重来。这些应该在 E2E 自动化。

层次错位会让测试既做了很多又没什么用。这不是量的问题，是结构的问题。

## 7. 覆盖率在不同层次的含义

单元测试的覆盖率（语句覆盖、分支覆盖）有明确的量化指标，见 [动态测试：白盒测试](./动态测试：白盒测试.mdx)。80% 分支覆盖是个常见的门槛。

到集成层次，覆盖率的定义就模糊了。跑一次集成测试可能覆盖了很多代码路径，但你关心的其实是"跨模块的交互场景"覆盖，这个没法用行数衡量。

到 E2E 层次，覆盖率通常用"业务场景数 / 总业务场景数"来估算，纯人工判断。E2E 追求覆盖率是错误的方向，应该追求"关键业务路径全覆盖"——比如电商的注册、登录、浏览、加购、下单、支付、退货这七条路径，每条至少一个 E2E 用例。

关于覆盖率作为指标的陷阱，见 [测试管理](./测试管理.mdx) 的度量部分。

## 8. 为什么金字塔不是唯一答案

现代软件系统的形态在变化，金字塔的假设也在被挑战：

- **Serverless / FaaS**：函数本身就是最小部署单元，单测和集成测的界限模糊。
- **微前端**：前端从"一个 SPA"变成"多个团队独立开发的碎片拼起来"，单元测试和 E2E 之间需要一个"契约测试"层。
- **AI/ML 系统**：模型行为不确定，传统"给定输入断言输出"的模式失效，需要"指标测试"层（准确率、召回率、公平性）。
- **数据管道**：正确性依赖数据质量，需要"数据测试"层（great_expectations、dbt tests）。

新形态下的分层策略仍在演化。但**"越低层越多、越高层越少"** 这个原则大概率还成立——不是因为金字塔好看，而是因为下层的成本-价值比永远优于上层。

## 9. 局限

分层是有用的抽象，但分层过细会把测试工程搞得太重。小项目（比如一个后台工具）根本不需要五层，两层——单测 + 一小把 E2E 冒烟——就够了。追求"每一层都有"是形式主义。

另一个坑是**层次之间的重复覆盖**。同一个"折扣计算"在单测覆盖了、在集成又测一遍、E2E 里又验证一次，看似很全，实际上是浪费——修一次逻辑要改三处测试，回归成本被人为放大。原则是每个具体问题**在最低能测到的层次**测掉，上层只做"这一层特有的问题"。

## 10. 分层视角下的其他主题

粒度是测试的**结构维度**。跟它交叉的还有：

- 目标维度：[按目标：专项测试](./按目标：专项测试.mdx)——性能、安全、可用性可以在任意层次做
- 时机维度：[测试过程与生命周期](./测试过程与生命周期.mdx)——每一层在生命周期的什么阶段做
- 方法维度：[动态测试：白盒测试](./动态测试：白盒测试.mdx) / [动态测试：黑盒测试](./动态测试：黑盒测试.mdx)——每一层都可以用白盒或黑盒方法
- 自动化：[自动化测试](./自动化测试.mdx)——上层难自动化、下层易自动化，这是金字塔形状的技术根因
- 变体：[敏捷测试](./敏捷测试.mdx) 讲每个 Sprint 里如何分层跑；[精准测试](./精准测试.mdx) 讲如何跨层次选择必跑用例

分层不是终点，是分析测试策略的坐标系。任何一次测试改造前，先问"我在哪一层动手"——答案往往决定成败。
