## 6.1 设计过程概览

数据库设计的核心任务是把现实世界中的信息转化为一个既能准确表达业务、又便于高效存取的数据库模式。**实体-联系（Entity-Relationship, E-R）模型**是完成这一转化最常用的概念工具。

### 6.1.1 设计阶段

一个较大的数据库项目通常经历以下阶段：

1. **需求分析（requirements）**：与用户面谈，写出功能与数据需求；
2. **概念设计（conceptual design）**：绘制 E-R 图，定义实体、联系、属性、约束；
3. **规格说明（specification of functional requirements）**：明确将执行的事务与查询；
4. **逻辑设计（logical design）**：把 E-R 图机械地转换为具体 DBMS 支持的模型，通常是关系模式；
5. **物理设计（physical design）**：选择存储结构、索引、分区等；
6. **规范化（normalization）**：使用函数依赖理论消除冗余（详见第 7 章）；
7. **实现与维护**。

### 6.1.2 设计选择

概念设计中反复出现的选择包括：

- 某项信息应作为**属性**还是**实体集**？
- 某种联系应建模为**联系集**还是**实体集**？
- 是使用**二元联系**还是更高元的**三元/n 元联系**？
- 是使用**特化/概化**还是把差异作为属性？

这些选择没有唯一答案，需要根据"最能反映业务、最少冗余、最便于扩展"的原则加以平衡。

## 6.2 实体-联系模型

### 6.2.1 实体集

**实体（entity）** 是现实世界中可区别于其他对象的事物，如"一位名叫 Einstein 的教师"、"编号 CS-101 的课程"。同类型实体的集合称为**实体集（entity set）**。实体通过一组**属性（attribute）** 加以描述，例如 `instructor` 实体集的属性为 $\{\text{ID}, \text{name}, \text{dept\_name}, \text{salary}\}$。

在 E-R 图中，实体集用**矩形**表示，属性用**椭圆**或直接列在矩形内表示，主码属性加下划线。

### 6.2.2 联系集

**联系（relationship）** 是若干实体之间的关联；同类型联系的集合称为**联系集（relationship set）**。例如"教师 Einstein 属于 Physics 系"是 `instructor` 与 `department` 之间的一次 `inst_dept` 联系。

数学上，一个 $n$ 元联系集 $R$ 是 $E_1 \times E_2 \times \cdots \times E_n$ 的子集，其中 $E_i$ 为参与实体集。

联系集本身也可以拥有**描述性属性（descriptive attribute）**，如 `student` 与 `section` 之间的 `takes` 联系可带一个 `grade` 属性。

在 E-R 图中，联系集用**菱形**表示，通过实线连接到相关实体集。

---

## 6.3 复杂属性

按结构与取值方式，属性可以分为：

- **简单属性 vs. 复合属性**：`name` 可拆为 `first_name`、`middle_initial`、`last_name`；`address` 可拆为 `street`、`city`、`state`、`zip`；
- **单值属性 vs. 多值属性**：`phone_number` 可以有多个；用双椭圆表示；
- **派生属性（derived attribute）**：可由其他属性计算得到，如 `age` 由 `date_of_birth` 派生；用虚线椭圆表示；
- **可空（null）属性**：可能没有值。

举例：`instructor` 实体集的属性可能是

```
instructor(
  ID,
  name{first_name, middle_initial, last_name},
  address{street{street_number, street_name, apt_number}, city, state, zip},
  { phone_number },
  date_of_birth,
  /* age */              -- 派生
  salary
)
```

## 6.4 映射基数

**映射基数（mapping cardinality）** 描述一个实体通过一个联系集能与多少个另外的实体相联系。对于二元联系集 $R$ 从 $A$ 到 $B$，有四种情形：

- **一对一（1:1）**：$A$ 中每个实体至多与 $B$ 中一个实体相关，反之亦然；
- **一对多（1:N）**：$A$ 中每个实体可与 $B$ 中多个相关，$B$ 中每个实体至多与 $A$ 中一个相关；
- **多对一（N:1）**：与 1:N 对称；
- **多对多（M:N）**：无限制。

例："一位教师属于一个系，一个系可以有多位教师"是 $N:1$（`instructor` → `department`）。

除了"最多"约束，还应关注"最少"约束——**参与度（participation）**：

- **全部参与（total participation）**：实体集的每一个实体都必须至少参与该联系一次，图上用双线表示；
- **部分参与（partial participation）**：允许有些实体不参与。

例：每位教师必须属于某个系，因此 `instructor` 全部参与 `inst_dept`。

## 6.5 主码

### 6.5.1 实体集

实体集的**主码**是能唯一标识每个实体的属性集合。为教师选定 `ID`、为学生选定 `ID`、为课程选定 `course_id`。在 E-R 图中，主码属性加下划线。

### 6.5.2 联系集

一个联系集的候选码由参与实体集的主码合并构成，然后按映射基数做进一步压缩：

- $M:N$ 联系：主码 = 两端主码的并集；
- $1:N$ 联系（$N$ 端在右）：主码 = 多端实体的主码；
- $1:1$ 联系：任一端实体的主码均可。

例如 `takes` 是 $M:N$：主码 = $\{\text{student.ID}, \text{course\_id}, \text{sec\_id}, \text{semester}, \text{year}\}$。

### 6.5.3 弱实体集

**弱实体集（weak entity set）** 自身没有足够的属性形成主码，必须依附于另一个**标识实体集（identifying entity set）**，通过**标识联系（identifying relationship）** 得以标识。

例：`section` 依附于 `course`。`section` 的**判别符（discriminator）**（也称部分码）为 $\{\text{sec\_id}, \text{semester}, \text{year}\}$，与 `course.course_id` 一起构成 `section` 的主码。

在 E-R 图中，弱实体集用双线矩形表示，标识联系用双线菱形表示；弱实体集必须**全部参与**该标识联系。

---

## 6.6 从实体集中删除冗余属性

在把联系画上后，需要检查各实体集是否含有冗余属性。经典的例子：若 `instructor` 中已经带有 `dept_name` 属性，而又存在 `inst_dept` 联系集连接 `instructor` 与 `department`，那么 `dept_name` 就是冗余的——它把本该由联系表达的信息又直接放到了实体集中。

处理原则：**联系集能表达的信息不应重复地放在实体集里**。这一步做好，能自然地避免下一章要讨论的"更新异常"。

## 6.7 将E-R图转换为关系模式

概念设计完成后，需要机械地把 E-R 图翻译为关系模式。翻译规则可以表格化：

| E-R 构造                | 关系模式                                                                                                    |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ |
| 强实体集 $E$            | 以 $E$ 的所有简单属性为列，$E$ 的主码为主码                                                                  |
| 弱实体集 $W$，依附 $E$  | 以 $W$ 的属性 + $E$ 的主码为列，主码 = $E$ 主码 + $W$ 判别符                                                 |
| 复合属性                | 每个叶子属性单独一列，或整体展开                                                                             |
| 多值属性 $M$，属于 $E$  | 新建一张表，列 = $E$ 主码 + $M$，主码 = 两者的并                                                             |
| $M:N$ 联系集 $R$        | 新建一张表，列 = 参与实体主码 + $R$ 的描述性属性；主码 = 参与实体主码的并集                                  |
| $1:N$ 联系集 $R$        | 把"1"端的主码作为外码放入"N"端实体表中；不建独立表                                                             |
| $1:1$ 联系集 $R$        | 把任一端的主码作为外码放入另一端实体表中                                                                      |
| 特化/概化               | 见 6.8.6                                                                                                    |
| 聚集                    | 把被聚集的联系视为一个整体的"实体"，参与外层联系时按上面规则处理                                             |

### 6.7.1 强实体集的表示

强实体集直接对应一张表。例如：

```
instructor(ID, name, salary)
department(dept_name, building, budget)
```

主码即实体集的主码。

### 6.7.2 具有复杂属性的强实体集的表示

- **复合属性**：把叶子属性展开为独立列。`name{first, middle, last}` → `first_name, middle_name, last_name`；
- **多值属性**：分离出新表，主键 = 原实体主码 + 该多值属性。例：

```
instructor_phone(ID, phone_number)
```

- **派生属性**：不进入模式，运行时按公式计算。

### 6.7.3 弱实体集的表示

`section` 表模式：

```
section(course_id, sec_id, semester, year, building, room_number, time_slot_id)
```

其中 `course_id` 是外码引用 `course`，主码为 $(\text{course\_id}, \text{sec\_id}, \text{semester}, \text{year})$，且 `course_id` 不能为空——这体现了弱实体的存在依赖。

### 6.7.4 联系集的表示

- **多对多**：产生独立表，如 `teaches(ID, course_id, sec_id, semester, year)`；
- **多对一** / **一对多**：不需要独立表，只需在"多"端加外码。例如 `inst_dept` 是 $N:1$，只需在 `instructor` 中保留 `dept_name` 外码；
- **一对一**：可以合并到任一端，或建立独立表；
- **带描述性属性**：把描述性属性作为附加列。`takes(ID, course_id, sec_id, semester, year, grade)`。

### 6.7.5 模式的冗余

弱实体集与其标识联系共享属性，翻译时不需要为标识联系单独生成表——因为弱实体集表中已经包含了它。避免在关系模式中重复存放同一信息，是防止更新异常的关键。

### 6.7.6 模式的合并

对 $1:1$ 或 $1:N$ 联系而言，联系集通常应与"多"端实体集合并到同一张表；只有当参与度为部分且大量元组的外码为 `NULL` 时，才考虑分离。

## 6.8 扩展的E-R特性

### 6.8.1 特化

**特化（specialization）** 表达从一个实体集划分出若干子集，每个子集拥有额外的属性或参与专门的联系。例如 `person` 特化为 `student` 与 `employee`；`employee` 又特化为 `instructor` 与 `secretary`。

### 6.8.2 概化

**概化（generalization）** 是特化的逆过程：从多个已知的实体集抽象出一个共同的父实体集。特化和概化在 E-R 图中都用**空心三角形**表示，通常将三角形指向上层（概化）方向。

### 6.8.3 属性继承

下层实体自动**继承（inherit）** 上层实体集的属性和参与的联系。因此 `student` 天然拥有 `person` 的 `ID`、`name`、`address` 等属性，而不必重复声明。

### 6.8.4 特化上的约束

- **不相交（disjoint）** vs. **重叠（overlapping）**：一个上层实体是否可以同时属于多个下层实体集；
- **完全（total）** vs. **部分（partial）**：每一个上层实体是否必须属于某个下层实体集。

例：`instructor` 与 `secretary` 通常是不相交且部分的特化——一个 `employee` 至多是其中之一，也可能都不是。

### 6.8.5 聚集

**聚集（aggregation）** 用于让一个联系集参与到另一个联系集。E-R 模型规定"联系不能连接联系"，但业务上确有这种需要。做法是把一个联系（连同参与它的实体）视为一个整体的"高层实体"，再和其他实体建立联系。

例：`student` 通过 `takes` 联系选修 `section`。若还想记录"某位教师是某位学生某门课的助教"，可把 (`student`, `section`, `takes`) 聚集为一个高层实体，再与 `instructor` 建立 `tutor` 联系。

### 6.8.6 转换为关系模式

特化/概化的关系模式实现有三种做法：

1. **上层 + 下层各自建表**：上层表存共有属性；每个下层表存自己独有的属性 + 主码（外码引用上层）。查询整体时需要连接；
2. **只建下层表**：把上层属性下推到每个下层表；不支持"共有实体不在任何下层"的情形；
3. **只建上层表**：把所有下层的属性合并到上层，附加一个"类型"标识列；容易产生大量空值。

实际系统多采用第一种方案，因为它扩展性好、空值最少。

## 6.9 实体-联系设计问题

### 6.9.1 E-R图中的常见错误

- 用**实体属性**表达本该建模为**联系**的信息（如 `student.advisor_ID`）；
- 用**联系**表达本应是**实体**的信息（如把 `department` 建成 `works_in` 联系的一个属性）；
- 忘记标注参与度、映射基数；
- 用二元联系拼凑本应是三元联系的语义。

### 6.9.2 使用实体集还是属性

判据：**该信息是否有自身独立存在的意义？是否需要与其他实体建立联系？**若是，就应建成实体集。例如"系"具备预算、建筑、教职员等独立属性，应作为实体集而不是 `instructor` 的一个属性。

### 6.9.3 使用实体集还是联系集

判据：**该概念是描述一个对象本身，还是描述若干对象之间的关联？**"选课"是学生与开课段之间的关联，应作为联系集。

### 6.9.4 二元还是n元联系集

任何 $n$ 元 ($n>2$) 联系都可拆分为若干二元联系加一个中间实体集来表达，但拆分未必总是自然。判据：**这些参与实体之间是否天然是一个"三方共同参与"的语义？**如果拆分会遗失信息（例如无法约束"同一个 (学生, 课程, 教师) 组合"必须绑定出现），则保留原始 $n$ 元建模更好。

## 6.10 数据建模的可选表示法

### 6.10.1 可选的E-R表示法

不同教材/工具采用略有差异的 E-R 图记号，常见变体：

- **Chen 记号**：椭圆表示属性、矩形表示实体集、菱形表示联系集，本书采用此风格；
- **信息工程（IE）记号 / 鸡爪记号（crow's foot）**：矩形内直接列属性；连线两端使用不同符号表示基数与参与度；
- **IDEF1X**：美国联邦标准，广泛用于工程领域。

### 6.10.2 统一建模语言

**UML 类图（Class Diagram）** 在软件工程中广泛使用：类对应实体集，关联对应联系集，泛化对应特化/概化。UML 中还可表达聚合、组合、多重性。使用 UML 的好处是可与面向对象分析设计一体化。

## 6.11 数据库设计的其他方面

### 6.11.1 功能要求

除了数据的结构外，设计者还应关注**功能需求**：将来会执行哪些查询、更新、报表？这些将决定索引与物化视图的取舍。

### 6.11.2 数据流、工作流

数据在组织中如何流动、由谁触发、经过哪些审批步骤，这些**工作流（workflow）** 信息影响事务的边界和权限设置。

### 6.11.3 模式演化

系统上线后需求会变，模式必须**演化（schema evolution）**：新增列、拆分表、迁移数据。良好的初始设计应尽量避免因业务微小变化就要重构核心表。

---

## 6.12 总结

- E-R 模型用实体集、联系集、属性以及映射基数、参与度、弱实体、特化/概化等概念，把现实世界抽象为易读的图形化模型；
- 通过一套机械的翻译规则，E-R 图可转换为关系模式；
- 设计的关键选择包括"实体 vs. 属性"、"实体 vs. 联系"、"二元 vs. 多元"、"特化 vs. 属性"，应以业务语义与最少冗余为准；
- 概念设计只是第一步；将来还要经过规范化（第 7 章）、物理设计、性能调优等阶段。
